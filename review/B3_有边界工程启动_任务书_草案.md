# 玄枢 B3 有边界工程启动 —— 工程任务书（草案）

> 起草：Claude，2026-11-20。依据：数据仓库 xuanshu-data 中的《玄枢数据契约 v1.0》与配套清单正本。
> 流程：本草案交 GPT 审查 → 用户逐项定稿 → 定稿后记为【用户裁决 B3-1】写入契约 → Claude 按定稿实施。
> **本任务书授权的是“有边界的工程启动”，不解除 B3，也不解除 B1、B2、B4 或任何 BLK。**

---

## 一、依据（契约原文摘录）

1. **执行边界（§12.5）：** “未经用户授权，不建仓库、不写业务代码或原型代码、不提交、不建 PR、不构建 IPA。”——本任务书即请求这一授权，并限定其范围。
2. **B3（§9.2、§9.5）：** GLOBAL。解除标准：“用户确认契约（已满足）；0A DDL 按契约重建，八字与六爻各 1 个端到端用例共用同一快照格式；R1 §5.14 旧 CHECK 与两版 yue_ling grep 无残留。”
3. **B3 解除前允许（§9.7）：** 非持久化准备；研究（结果不进入正式库）；资料整理；测试设计。
4. **B3 解除前禁止（§9.7）：** 正式数据库实施（建正式表结构并纳入发布链路）；正式数据写入（任何 FORMAL 对象、ApprovalRecord、AdmissionRecord 写入正式库或发布包）；正式计算快照持久化（任何 CalculationSnapshot 写入用户库）；任何以“准备”“测试”为名、实际产生上述持久化结果的做法。
5. **§9.7 留待用户确认的一点（原文）：** “B3 的解除标准本身要求‘0A DDL 按契约重建，八字与六爻各 1 个端到端用例共用同一快照格式’。这些验收动作能否在用完即弃、不进入正式发布链路的临时环境中执行并算作‘非持久化准备与测试’，本稿不自行认定……由用户在授权工程阶段时确认；确认前不执行。”
6. **原型（裁决 6、§11.3、W-12）：** 技术栈冻结前，在**独立临时仓库**做原型实测；结果只用于选型，**原型代码不进入正式仓库**；启动前须有用户授权与**书面量化阈值**。
7. **技术栈（§11.4）：** 未冻结。候选 React + TypeScript + Three.js + Capacitor + 原生 SQLite；备选 SwiftUI + GRDB + RealityKit。最终选型等原型实测。
8. **独立性（B4-11）：** 生成基准的实现必须独立于被测引擎，不得共用代码或模块；比对（Diff）也不得由被测引擎自身执行。

## 二、授权范围（允许）

1. 新建私有仓库与 CI（GitHub Actions），工具版本锁定、构建可复现。
2. 实现计算引擎核心：时间归一（UTC+8、内地 1986–1991 夏令时、UTC/UT1 坐标）、节气查表、日柱锚点递推、年/月/时柱、子时锁定规则（CFG-01 = ye_zi_b）、真太阳时（经度项 + 均时差查表插值）、降级与按柱歧义候选、六爻装卦核心。
3. 按契约写数据库结构（DDL），**只在测试运行时于内存中临时建库**，跑完即弃（见第四节 D1）。
4. 用已冻结的 B1、B4 数据做非正式工程测试与回归测试：B1 的 W-05、B4 的 group 0～4、B2 的 W-03、B3 的 W-04，以及 W-01、W-02、W-07、W-09、W-13 中能在此阶段验证的部分。
5. 在独立临时仓库做 §11.3 原型实测（见第五节）。

## 三、禁止

1. 正式数据库实施：不建 formal.sqlite / user.sqlite 的正式库文件，不纳入任何发布链路。
2. 正式数据写入：不写任何 FORMAL 对象、ApprovalRecord、AdmissionRecord。
3. 正式计算快照持久化：测试产生的快照只在内存中，不落盘为可发布文件。
4. 不发布 App，不构建面向用户的正式安装包（原型实测用的测试包除外，见第五节）。
5. 不自动解除任何阻断：每项须经验收，并由用户确认解除。
6. 引擎仓库不得引用或复制 xuanshu-data 中的生成脚本（B4-11）；引擎只读取冻结数据文件，并校验其哈希。
7. 引擎第一阶段不联网、不接任何 AI 服务（裁决 5、W-13）。

## 四、需要用户定稿的事项

### D1　§9.7 的确认（建议：同意）
> 建议裁决文字：W-04 所需的“DDL 按契约重建”与“八字、六爻端到端用例”，可在用完即弃的临时环境中执行，算作非持久化准备与测试。具体做法：测试运行时在内存中建库（SQLite `:memory:`），用例跑完即销毁；不生成数据库文件，不进入发布链路，不作为正式数据。

### D2　原型与引擎的先后（建议：(b) 并行）
- **(a) 先原型后引擎：** 先在临时仓库实测两套技术栈，冻结技术栈后再写引擎。最稳，引擎晚开始。
- **(b) 并行：** 引擎核心只做纯计算（不碰界面、不碰数据库驱动），与原型同时推进；原型选定技术栈后，再接入界面与数据库。
- 建议 (b) 的理由：B1、B2、B4 的验收只需要纯计算核心；回归用例写成与语言无关的 JSON 测试向量，将来即使换语言重写，同一套用例照样能跑。

### D3　引擎核心的语言（建议：TypeScript）
- TypeScript：主选技术栈原生使用；若最终选 SwiftUI，可经 JavaScriptCore 运行，或按同一套 JSON 测试向量用 Swift 重写。
- Swift：只适合确定走 SwiftUI 时。
- 不论选哪个，测试向量都与语言无关。

### D4　仓库划分（建议）

| 仓库 | 内容 | 状态 |
| --- | --- | --- |
| `xuanshu-data`（已有） | 契约、冻结数据、生成脚本、数据核对 CI | 不变 |
| `xuanshu-engine`（新建，私有） | 引擎核心、单元测试、测试向量、引擎 CI | 本授权新建 |
| `xuanshu-proto`（新建，私有，临时） | §11.3 原型实测代码与实测记录 | 本授权新建；选型结束后归档，代码不进引擎仓库 |

比对程序（拿引擎输出对照冻结基准）放在 `xuanshu-data` 的 `harness/` 目录：引擎 CI 产出结果文件，数据仓库的比对程序读取并比对，满足“Diff 不由引擎自身执行”。

### D5　原型量化阈值（草案，请用户与 GPT 定）
§11.3 的必测项，契约要求先定数字再测：

| 必测项 | 草案阈值 |
| --- | --- |
| iPhone 3D 帧率 | 目标机型上持续 60 秒的场景，平均 ≥ 50 fps，最低 ≥ 30 fps（目标机型待定：建议用户自己的 iPhone） |
| WebView 内存稳定 | 连续使用 30 分钟，内存增长 ≤ 10%，无崩溃 |
| SQLite 事务 | 快照写入、触发器拒绝 UPDATE、删除级联与失败整体回滚，全部按预期（100%） |
| FTS5 trigram | 10 万条古籍段落中检索，p95 ≤ 200 ms |
| 离线 | 飞行模式下全部功能可用 |
| 导入导出 | 文件头含快照 ID、指纹、状态；导入后状态不丢失（往返 100%） |
| 全球时区与地点数据 | 安装包增量 ≤ 30 MB，单次查询 p95 ≤ 50 ms |

说明：真机实测需要用户在自己的 iPhone 上安装测试包并运行测试页，测试页自动记录结果。

### D6　契约里一处不一致，建议同时修正
配套清单 W-03（B2 工程验收）仍写“四值各至少 1 个端到端用例通过”，但 §9.5 B2 已按【用户裁决 N-6】改为“锁定值 ye_zi_b 正向用例全过 + 其余三值在库层与引擎层被拦截的负面用例全过”。
> 建议改为：W-03：未选 zi_rule 时创建命盘被拒，0 例漏网；锁定值 ye_zi_b 的端到端用例全过（含 23:30 立春前夜年月柱用例与 23:59→00:00 跨日用例）；zi_zheng、zi_chu、ye_zi_c 三值在库层与引擎层被拦截的负面用例全过（【用户裁决 N-6】）；后续开放多流派时恢复“四值各至少 1 个端到端用例”。
