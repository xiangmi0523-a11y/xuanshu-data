## 3 通用库层规范（第 4 节各表共同遵守）

### 3.1 命名与失败定位

- 每个 CHECK 写成具名约束 `CONSTRAINT "<约束编号>" CHECK (...)`。SQLite 报错信息为 `CHECK constraint failed: <约束编号>`，可直接定位到第 5 节的测试编号。
- 每个触发器的报错写成 `RAISE(ABORT, '[<约束编号>] <说明>')`。
- NOT NULL 报错为 `NOT NULL constraint failed: <表>.<列>`，按表、列定位。
- 外键报错不带列名。每个外键单独一个负面用例；用例结束跑 `PRAGMA foreign_key_check`，返回表、行号、父表定位。
- 验证查询每条带编号，返回违规行的主键。

### 3.2 NULL 与 CHECK（P-33）

1. 强度“必须”的列一律 NOT NULL。
2. 可空枚举写 `col IS NULL OR col IN (...)`。
3. 条件必须写 `NOT (<条件>) OR col IS NOT NULL`，且 <条件> 中引用的列必须 NOT NULL，或写成 IS、COALESCE 形式，保证条件只取真或假。
4. 布尔列为 INTEGER NOT NULL CHECK (col IN (0, 1))。
5. 全部表 STRICT。
6. 校验方式：第 5 节 DB-N 矩阵对规格表中每个必填列做 NULL 插入；DB-E 矩阵对每个枚举列做越界与 NULL 插入。规格表由本清单第 4 节生成，不从 DDL 反推，避免自证。

### 3.3 三类只追加记录与序号（P-32；Q-5 建议，待裁决；第 3 版）

契约中的只追加记录性质不同，第 3 版按 ChatGPT 第二轮意见分为三类，各定规则。

**共同规则（三类都适用）：**

1. 记录本身是权威来源；当前值只由视图推导，不建可写的“当前状态”列。
2. sequence_no 全表唯一、严格递增（触发器：新值大于全表最大值）；允许断号，不许重复、倒序。
3. data_release 取自 data_release 表，该表带整数 release_seq；同一键的新记录 release_seq 不得小于上一条。
4. sequence_no 跨数据版本延续、不重置，由 CI 对比上一版检查；E2 只有一个数据版本，不验收此条。
5. 一律拒绝 UPDATE 与 DELETE。

**甲类：状态转换历史**

- 适用表：evidence_status_history、admission_record、formal_status_history、branch_status_history、blocker_change。
- 每行表达一次状态转换 previous → new：
  - 每键首条 previous 为空；
  - 之后每条 previous 必须等于同键上一条的 new（触发器）。
- 当前值 = 同键 sequence_no 最大一条的 new。
- 各表的键：

| 表 | 键 |
| --- | --- |
| evidence_status_history | (target_type, target_id, field) |
| admission_record | (component_id, purpose) |
| formal_status_history | (target_type, target_id) |
| branch_status_history | branch_id |
| blocker_change | block_id |

- previous = new 的“无转换行”被拒。分支的“状态说明”（§10.2）不是状态转换，另记于 branch_event（第 3.6 节）。

**乙类：批准事件**

- 适用表：approval_record。
- 每行是一次裁决事件（approve / approve_conditional / reject / revoke），不是 previous → new 的转换，不适用甲类衔接规则。
- 规则：
  - sequence_no 全表唯一递增；
  - supersedes_approval_id 若非空，必须指向同一 target_id 的较早记录；
  - revoke 必须有撤销原因；
  - decided_by 只能是用户。
- 某变体的“现行批准” = 该 target_id 下 sequence_no 最大的一条，且满足：
  - decision = approve（自查）；
  - target_content_hash 等于变体 content_hash；
  - approve_conditional 本身不构成现行批准。按 R-E4“条件满足后须新建确认记录”，确认记录即一条新的 approve 记录，supersedes_approval_id 指向原附条件批准；现行批准只认 approve（自查：第 3 版写“只认已确认者”，未说确认记录是什么）。

**丙类：默认配置追加历史**

- 适用表：component_default。
- 每行是“某子项、某适用范围的默认变体”的一次指定，不是状态转换。
- 当前默认 = 同一 (component_id, applicable_scope) 下 sequence_no 最大者。
- 每行必须引用一条乙类现行批准（approval_ref），且所指变体属于该子项。

**RuleVariant 的 formal_status_history 与 ApprovalRecord（第 3 版重新核对）：**

- 契约 §4.4 要求 formal_status_history 记录 RuleVariant，§8.2 规定 RuleVariant 为 FORMAL 当且仅当以下三条同时成立：
  - 存在现行 approve；
  - target_content_hash 等于当前 content_hash；
  - 批准要件齐全。
- 两者并不重复：批准只是必要条件，要件（如支持性证据变为 NON_FORMAL，R-I-4）变化时，正式状态可以在无撤销的情况下变化。
- 第 3 版不删除契约要求，改为约束两者一致（DB-F-24）：
  1. ApprovalRecord 是批准与撤销裁决的唯一权威来源；
  2. formal_status_history 是 RuleVariant 正式状态转换的权威记录；
  3. 每条 RuleVariant → FORMAL 的转换，在同一或更早数据版本必须有一条现行批准（哈希一致）；
  4. 每条 revoke 生效的数据版本，若该变体当时为 FORMAL，必须有一条 → NON_FORMAL 的转换；
  5. 批准要件的核查留发布校验，E2 只验第 3、4 条。
  6. （第 4 版，R3）要件中“支持性证据须为 FORMAL”（R-I-4）一项，E2 另验：
     - 变体原为 FORMAL 且有现行批准；
     - 其子项的某条支持性证据（evidence_link.evidence_role = 支持、branch_id 为空）在某数据版本转为 NON_FORMAL；
     - 此时即使没有 revoke，该变体也必须在同一数据版本追加 FORMAL → NON_FORMAL 的转换；
     - 未追加即为不一致，由发布校验 Q-F-24d 检出（DB-F-24 (d)）。
     - 双记录设计不变。

### 3.4 只读与只追加

- 正式库全部表拒绝 UPDATE 与 DELETE。
- 用户库计算层（输入、配置内容、配置取值、快照及其子表）拒绝 UPDATE。
- 用户库计算层的 DELETE 只放行第 3.6 节的删除入口。
- Branch 主行允许删除入口内置空 base_snapshot_id（§10.2），其余 UPDATE 拒绝。

### 3.5 快照封存协议（P-34 (a)）

1. 一个事务内写入顺序：
   - 先写 execution_trace_step、snapshot_dependency、snapshot_non_formal_reason、snapshot_degradation_reason、snapshot_resolved_context、snapshot_gov_*；
   - 最后写 calculation_snapshot。
   - 子表到快照的外键设为 DEFERRABLE INITIALLY DEFERRED，在提交时检查。
2. 快照行 BEFORE INSERT 触发器校验：
   - 依赖行至少覆盖 engine 一类；
   - NON_FORMAL 有原因行，FORMAL 无原因行；
   - 降级原因与 result_completeness 一致；
   - FORMAL 快照的依赖中无个人对象（同库可查）。
   - （自查）“轨迹覆盖该模块全部步骤编号”需读正式库步骤表，改为引擎预检 + Q-T-01（第 3.10 节）。
3. 子表 BEFORE INSERT 触发器：所指快照已存在即拒绝，即封存后不可追加。
4. 任一步失败，整体回滚，不留孤儿子行。DB-R 组测试验证。

### 3.6 删除入口：连接级控制（P-35；Q-13 建议，待 GPT 审查；第 3 版补齐，第 4 版补事务绑定与审计写入授权）

**(1) 两种授权、三个函数（第 4 版重写）**

删除模块在连接建立时注册三个自定义 SQL 函数，均不设 directOnly，以便触发器调用：

| 函数 | 用途 | 放行的授权 |
| --- | --- | --- |
| `xs_del_gate(profile_id, token, audit_id, grant_seq)` | 放行某档案名下行的 DELETE，以及 Branch 置空（自查：branch_event 插入改由 xs_del_gc 放行） | 删除授权 G |
| `xs_del_gc(token, audit_id, grant_seq)` | 放行本次删除事务中不属于任何档案的对象操作：无主配置回收、branch_event 插入 | 删除授权 G |
| `xs_audit_write(token, audit_id, grant_seq, kind)` | 放行 deletion_audit、deletion_audit_count 的 INSERT | 审计写入授权 W |

- 第 3 版的 `xs_del_audit()`、`xs_del_audit_writer()` 作废，由上表三个函数取代；第 3 版中前者已注册而后者未注册的矛盾随之消除。
- 授权状态只存在删除模块的 JS 闭包中，SQL 无法读写：
  - **删除授权 G：** armed、profile_id、grant_seq、audit_id、txn_token。
  - **审计写入授权 W：** armed、kind（success / failure）、audit_id、grant_seq、txn_token（自查补 grant_seq，与条件 e 一致）。
- grant_seq 为进程内单调递增计数，每次删除入口加 1。
- G 与 W 互斥：任一时刻至多一个处于 armed，闭包内断言。

**(2) 事务标识：txn_token 与事务标记行（第 4 版新增，R1）**

- SQLite 不提供可查询的事务 ID，故由删除模块自建事务标识：
  - 每次 `BEGIN IMMEDIATE` 后，模块生成 128 位随机 txn_token；
  - 在同一事务内向 U20 deletion_txn_marker 写入唯一一行 (id = 1, txn_token, audit_id, grant_seq, kind)。
- U20 是主库表，不是 TEMP 表，原因是主库触发器不能引用 temp 库的对象。它随事务回滚而消失；提交前由模块在同一事务内删除。因此任何事务结束之后，U20 都不应留有行。
- U20 不是授权依据：任何代码都能写入 U20，但写入者不知道闭包中的 txn_token。授权依据始终是闭包；U20 只用于把触发器调用与“本次事务”绑定。
- 触发器从 U20 取 txn_token、audit_id、grant_seq 三项，传给授权函数（自查：第 4 版初稿函数签名漏列 grant_seq）。授权函数逐项比对，**全部满足才返回 1**：

| # | 条件 | xs_del_gate | xs_del_gc | xs_audit_write |
| --- | --- | --- | --- | --- |
| a | 对应授权（G 或 W）armed | G | G | W |
| b | `db.isTransaction` 为真 | ✓ | ✓ | ✓ |
| c | 参数 token = 闭包 txn_token（U20 中的值须与本次事务生成的随机数一致） | ✓ | ✓ | ✓ |
| d | 参数 audit_id = 闭包 audit_id | ✓ | ✓ | ✓ |
| e | 参数 grant_seq（触发器从 U20 取出传入）= 闭包 grant_seq | ✓ | ✓ | ✓ |
| f | 参数 profile_id = 闭包 profile_id | ✓ | — | — |
| g | 参数 kind = 闭包 kind | — | — | ✓ |

- 任一条件不满足，或函数内部抛出异常，一律返回 0（异常即视为拒绝）。

**(3) 事务控制只经包装函数（第 4 版新增，R1）**

- 删除模块的 BEGIN、COMMIT、ROLLBACK 只通过模块内的三个包装函数执行。包装函数维护闭包中的事务状态：
  - **begin()：** 断言连接不在事务中；执行 `BEGIN IMMEDIATE`；生成 txn_token；写 U20。
  - **commit()：** 先撤销 G 与 W；再在同一事务内删除 U20 行；再执行 COMMIT；最后清空 txn_token。
  - **rollback()：** 先撤销 G 与 W；再执行 ROLLBACK（U20 行随之消失）；最后清空 txn_token。
- 删除入口的整个流程放在一个同步调用中。node:sqlite 是同步接口，其间不会穿插其他 JS 代码；外层用 try / finally 包裹。
- finally 无条件执行：撤销 G 与 W；若连接仍在事务中，执行 ROLLBACK；清空 txn_token。
  - 无论正常结束、抛出异常还是函数中途返回，授权都在离开调用时撤销。
  - 若进程崩溃，闭包随之消失，未提交事务在下次打开时由 SQLite 回滚，U20 行也随之消失。
  - （自查）COMMIT 本身失败（例如延迟外键在提交时检查失败）：此时 G 已撤销，U20 行已在事务内删除；随即 rollback()，再按第 (5) 条失败流程写失败审计。
- **完整性检查：** 删除入口开始前与结束后都检查 U20 为空。
  - 开始前不为空：拒绝开始，报“残留事务标记”；只能由 commit() 之外的错误路径造成。
  - 结束后不为空：报错并标记该次删除失败。
- **静态检查（CI）：** 删除模块中字面 `BEGIN`、`COMMIT`、`ROLLBACK` 只允许出现在三个包装函数内；删除入口执行期间只调用删除模块自身与 node:sqlite 的函数，不调用其他业务模块（CI 检查删除模块不 import 业务模块）。

**(4) 成功删除流程（第 4 版：审计写入与删除分开授权，R2）**

1. begin()：得到 txn_token；新生成 audit_id（UUIDv7）；U20 写 (txn_token, audit_id, grant_seq, kind = success)。
2. **arm W(success, audit_id, grant_seq, txn_token)** → 插入 deletion_audit（success = 1）与各对象类型的 deletion_audit_count（删除前统计的条数）→ **立即撤销 W**。
3. **arm G(profile_id, grant_seq, audit_id, txn_token)**。
4. 置空指向该档案快照的 Branch.base_snapshot_id；每个被置空的分支追加一条 branch_event。
5. 按子到父顺序删除级联范围（§10.2）。
6. 回收无主配置（第 (6) 条）。
7. commit()：撤销 G → 删除 U20 行 → COMMIT。
8. finally：确认 G、W 已撤销，txn_token 已清空。

**(5) 失败删除流程（第 4 版，R2）**

1. 第 (4) 条任一步出错 → rollback()：撤销 G、W → ROLLBACK。成功审计、计数、已删行、Branch 置空、branch_event 全部回滚。
2. 另起事务 begin()：新 txn_token′；**新 audit_id′**，与失败那次回滚掉的 audit_id 无关；U20 写 (txn_token′, audit_id′, grant_seq, kind = failure)。
3. **arm W(failure, audit_id′, grant_seq, txn_token′)** → 插入 deletion_audit（success = 0），不写计数行 → **立即撤销 W**。
4. commit()。
5. 失败审计事务本身若再失败：rollback()，不再重试；向调用方报告“删除失败且失败审计未写入”。

**(6) 受保护表、配置回收、Branch 规则（第 3 版内容，触发器条件按第 4 版函数改写）**

- **owner_profile_id 下放：** 用户库计算层每张表（U02、U03、U06～U13）都带 owner_profile_id；插入时触发器核对它与父行一致。
- **受保护表（自查补 U01）：** U01 profile（以 owner_profile_id 为主键），以及 U02、U03、U06～U13。U01 在级联最后删除。
- **删除触发器（受保护表）：**

  ```
  xs_del_gate(OLD.owner_profile_id,
              (SELECT txn_token FROM deletion_txn_marker WHERE id = 1),
              (SELECT audit_id  FROM deletion_txn_marker WHERE id = 1),
              (SELECT grant_seq FROM deletion_txn_marker WHERE id = 1)) = 1
  AND EXISTS (SELECT 1 FROM deletion_audit
              WHERE audit_id = (SELECT audit_id FROM deletion_txn_marker WHERE id = 1)
                AND success = 1)
  ```

  - 连接未注册函数时，触发器报 no such function，删除失败。TEMP 表不作任何授权依据。
  - U20 无行时，子查询返回 NULL，授权函数的条件 c、d、e 不成立，返回 0。
- **配置回收（U04、U05）：** 只有同时满足以下三条时才可删除：
  - `xs_del_gc(token, audit_id, grant_seq) = 1`（三项均从 U20 取出传入）；
  - U06 中已无该配置的引用；
  - U07 中已无快照引用该配置。
  - U05 只能随所属配置一同删除。
  - 回收在删除被授权档案的引用与快照之后执行。
  - 仍被其他档案引用的配置保留（与 §10.2“删行”的关系见 Q-13）。
- **Branch：** 按 §10.2，Branch 不删，只置空 base_snapshot_id。UPDATE 只在同时满足以下四条时放行：
  - xs_del_gate 对 OLD.base_snapshot_id 所指快照的档案返回 1；
  - 只改 base_snapshot_id，其余列 NEW 与 OLD 相同；
  - NEW.base_snapshot_id 为空；
  - 在快照删除之前执行。base_snapshot_id 外键不级联。
- **branch_event（自查改写）：** 状态说明写入 U19 branch_event（不含快照 ID、档案 ID、哈希；只追加）。
  - 第 4 版初稿要求“xs_del_gate 对被置空分支原指快照的档案返回 1”，但插入时分支引用已置空，branch_event 又不得含快照 ID，触发器无从得知档案，无法执行。
  - 改为：INSERT 触发器要求 xs_del_gc(U20 三项) = 1，且 NEW.audit_id = U20 audit_id。
  - 每个被置空的分支恰好一条 branch_event，由测试比对置空数与事件数（DB-D-24）。
  - branch_event 不是状态转换，不进 branch_status_history。

**(7) 删除审计的保护（第 4 版：插入授权改用 xs_audit_write，R2）**

- U18 deletion_audit、deletion_audit_count 永不可改、永不可删。即使 G 或 W armed，UPDATE 与 DELETE 一律拒绝。
- **deletion_audit 的 INSERT 触发器：**

  ```
  xs_audit_write((SELECT txn_token FROM deletion_txn_marker WHERE id = 1),
                 NEW.audit_id,
                 (SELECT grant_seq FROM deletion_txn_marker WHERE id = 1),
                 CASE NEW.success WHEN 1 THEN 'success' ELSE 'failure' END) = 1
  AND NEW.audit_id = (SELECT audit_id FROM deletion_txn_marker WHERE id = 1)
  ```

  并要求 U20 的 kind 与 NEW.success 相符。
- **deletion_audit_count 的 INSERT 触发器：**
  - 同样要求 xs_audit_write(…, 'success') = 1；
  - audit_id 等于 U20 中的 audit_id；
  - 所属审计行 success = 1。失败审计不得带计数行。
- **普通业务路径不能伪造审计：**
  - 未持有闭包，W 不会 armed；
  - 即使自写 U20，也不知道 txn_token；
  - 即使在 G armed 时插入审计，也因 W 未 armed 被拒（G 与 W 互斥）。
- **字段限制（§10.4）：**
  - 只有 audit_id、deleted_at、trigger、app_version、data_release、success，以及计数表的 object_type、count；
  - object_type 为 CHECK 枚举；
  - count ≥ 0；
  - app_version、data_release 用 GLOB 格式检查。
- **计数核对：** 删除前统计写入计数表；测试比对删除前后实际差值（DB-D-21）。

**(8) 静态检查（CI）**

- 注册 xs_del_gate、xs_del_gc、xs_audit_write 的代码只允许出现在删除模块一个文件里。
- 非 DDL 文件不得出现 `DROP TRIGGER`、`PRAGMA writable_schema`。
- 事务语句只在包装函数内（第 (3) 条）。

**(9) 限度**

- 本进程内的代码仍可注册同名函数、删除触发器，或在删除模块内部引入错误的事务语句。这与契约 §1.2“只能发现篡改，不能阻止篡改”、ENG.1“只能防程序错误”一致，不承诺更多。
- 第 (3) 条的完整性检查与静态检查用于发现这类程序错误。
- 哈希链不建（Q-13），§10.3 第 3 条 E2 不验收。

### 3.9 结构化 JSON 字段（Q-9 建议，待裁决；第 3 版修订范围规则）

**适用列：** applicable_scope、scope、conditions、raw_payload、normalized_payload、result_payload。每列一律：

1. NOT NULL；
2. `json_valid(col)`；
3. 顶层为对象；
4. 带整数 `"v"` 结构版本；
5. 按版本校验必需键与类型（`json_type`）；
6. 未知键被拒（触发器以 json_each 比对白名单）；
7. 存储文本必须等于其规范化形式（第 6.2 节）——库层无法重算规范化，由封存前引擎校验，测试复核。

**范围结构 scope v1（第 3 版）：** 两种 kind。

- `{"v":1,"kind":"all"}`：全范围。

  - module 必填；
  - school_id、edition_id、from、to 可选；
  - from、to 为 `YYYY-MM-DD`；
  - 有 from、to 时须 from ≤ to。
  - 字段集合取自契约已有的范围维度：§3.3 school_id、edition_refs、applicable_from/to，§8.2“适用模块/版本范围”。

### 3.10 执行层划分：SQLite 同库规则（自查新增）

- **规则：** SQLite 中，非 TEMP 的触发器与视图只能引用其所在库的对象；只有 TEMP 触发器与视图可以跨库（sqlite.org lang_createtrigger“For non-TEMP triggers, the table to be modified or queried must exist in the same database…”；源码 DbFixer 报错“cannot reference objects in database”）。
- **后果：** 用户库的 CHECK、触发器、视图不能读取正式库。第 2～4 版中有几处把跨库检查写成了用户库触发器、视图或外键，在 SQLite 中无法建立。
- **统一处理：** 凡需读取正式库的约束，执行层一律为“E + Q”：
  - 封存前由引擎预检；
  - 封存后由连接级查询复核：连接 ATTACH 正式库后执行，或用连接建立时创建、不入库结构的 TEMP 视图。
  - 用户库内的 C、T 只做同库可见的检查。

| 位置 | 第 2～4 版初稿写法 | 自查后 |
| --- | --- | --- |

| §4.2 v_config_closure | 用户库视图，经正式库 F27 | TEMP 视图，连接 ATTACH 正式库后创建，不属于 user.sqlite 结构 |

| 第 5.10 节 DB-H-16 | 拒（库层） | 引擎预检拒 + DB-X-07 |

## 5 约束验证清单

每条给出四项：正向输入（应成功）、反向输入（应失败或被查出）、预期结果、失败定位（第 3.1 节约定的报错标记或查询编号）。“基准行”指该表一行全部字段合法的样例；反向输入只改所列字段。

### 5.1 生成矩阵（覆盖全部表）

**DB-N 必填列 NULL**

- 正向：基准行插入成功。
- 反向：规格表中每个“必”列各置 NULL 一次。
- 预期：每次报 `NOT NULL constraint failed: <表>.<列>`。
- 失败定位：未报错的表与列。

**DB-N2 双向核对**

- 规格表必填集合与 DDL 的 notnull 集合逐列比对。
- 预期：两集合相等。
- 失败定位：差集。

**DB-E 枚举越界**

- 正向：每个枚举列取每个合法值各一次。
- 反向：取越界值 'X'；可空枚举另取 NULL（应成功），必填枚举取 NULL（应被 DB-N 拦截）。
- 预期：越界报 `CHECK constraint failed: <约束编号>`。
- 失败定位：约束编号。

**DB-K 外键**

- 每张表测试前断言 `PRAGMA foreign_keys` = 1，未开即整组失败。
- 正向：引用存在的父行。
- 反向：每个外键单独指向不存在的父行。立即外键在语句处报 FOREIGN KEY constraint failed；延迟外键在提交处报。
- 预期：每例各报一次；全部结束后 `PRAGMA foreign_key_check` 返回 0 行。
- 失败定位：用例编号（一例一个外键）与 foreign_key_check 输出。

**DB-I 不可改删**

- 反向：
  - 正式库每表 UPDATE 一列、DELETE 一行；
  - 用户库计算层每表 UPDATE 一列、未授权 DELETE 一行。
- 预期：报 `[DB-I-<表>]`。
- 失败定位：表名。

### 6.2 规范化规则 jcs-1（Q-11 建议，待裁决）

1. **基础：** RFC 8785 JSON 规范化。
   - 输出 UTF-8，无多余空白；
   - 对象键按 UTF-16 码元升序；
   - 字符串只转义 `"`、`\` 与 U+0000～U+001F：\b \f \n \r \t 用简写，其余写 \u00xx 小写；
   - 其余字符原样输出（含 U+2028）。
2. **Unicode：** 不做任何归一化（F14）。孤立代理项拒绝。
3. **重复键：** 解析阶段拒绝。
4. **数值：**
   - 只允许整数，范围 ±(2^53 − 1)。
   - 非整数一律以十进制字符串表示，按字段固定刻度：经纬度 6 位小数；均时差秒 3 位小数（§9.4 B1-1）；度数 1 位小数（CFG-09）。
   - −0、NaN、Infinity 拒绝。
5. **null 与缺失：**
   - 契约明定为 null 的值（如三柱模式时柱 null，§13.3；luck_cycle.value null，§13.2）显式写 null；
   - 其余不适用的字段一律省略，不写 null；
   - 各载荷版本的结构表列明每个字段属哪一类。
6. **数组：**
   - 默认有序，顺序即语义（六爻自初爻起；candidates 按 §13.3 固定规则，前一侧在先）；
   - 语义为集合的数组按规范化文本升序排列，未排序即拒。
7. **时间：**
   - 瞬时用 RFC 3339 UTC 字符串，毫秒精度：`YYYY-MM-DDTHH:MM:SS.sssZ`；
   - 民用时间另存原文字符串与 UTC 偏移秒数。
8. **哈希：** sha256，取规范化文本的 UTF-8 字节，输出 64 位小写十六进制。
9. **版本兼容（P-37）：**
   - 规范化版本只增不改，登记在 F06，每版冻结金标向量与其 sha256；
   - 每个哈希记录自身的 canonicalization_version；
   - 校验时按记录上的版本选用对应实现；
   - 旧版本实现永久保留在引擎中；
   - 不得用新版本重算旧记录来判定一致与否；
   - 新版本只用于新记录。
