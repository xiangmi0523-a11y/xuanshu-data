## 1 结论摘要

1. **结构上能落实，但不能“直接照契约重建”。** 契约有 31 处结构问题（第 2 节），其中 13 处须用户或 GPT 决定才能写 DDL（第 8 节 Q-1～Q-13）。我建议先把这些一次定下，再一次写完 DDL，避免边写边补。
2. **根因归为五条（第 2.1 节）。** 主要是：
   - 部分枚举与结构契约没给值；
   - 同一状态既列为字段又有历史表；
   - 正式治理数据还不存在，端到端用例必须用测试夹具；
   - v0.1.1 原文不在仓库；
   - 删除与隐私条款同去重、哈希链条款互相冲突。
3. **W-04 的“0A”在全部资料中没有定义。** 建议解释为“契约 §1～§10 定义的正式库与用户库表结构”，请用户确认（Q-1）。
4. **八字端到端用例在现行契约下只能生成 NON_FORMAL 快照，且必须用钟表时间（CFG-02 = false）。**
   - 原因一：CFG-04/05/05W 属“暂按”参数（§5.3）。
   - 原因二：真太阳时路径依赖均时差，W-05 通过前为 BLOCKED-FORMAL，不生成快照（§9.4）。
   - 这不影响 W-04（只验快照格式一致）。详见第 5 节。
5. **须交 Muse 查证的只有两项，都在六爻：** 起卦日界、月建取法（第 7 节）。两项都不挡 E2 的表结构；端到端用例按第 5.3 节避开边界，并在快照中标明“待核实”。

## 3 建表清单

图例：

- 强度：必 = 必须，条 = 条件必须，可 = 可选，派 = 派生只读。
- E2 一栏：
  - “建”：E2 按本清单建表；
  - “建*”：建表，但部分取值或结构待第 8 节决定；
  - “不建”：契约字段不全，列为【待定】。
- 通用约定（全部表）：
  - 机器 ID 为 UUIDv7 文本（§1.2）；
  - 人读稳定 ID 另列，UNIQUE，不复用；
  - 枚举一律加 CHECK（§1.4）；
  - 列表字段一律用连接表，不用 JSON 数组（§3.2）；
  - 全部表用 STRICT；
  - 正式库全部表加 BEFORE UPDATE/DELETE 触发器拒绝写改（只读、只追加，§1.2、§1.1 第 5 条）；
  - 状态类“当前值”一律为视图（Q-5）。
