## 一、依据（契约原文摘录）

1. **执行边界（§12.5）：** “未经用户授权，不建仓库、不写业务代码或原型代码、不提交、不建 PR、不构建 IPA。”——本任务书即请求这一授权，并限定其范围。
2. **B3（§9.2、§9.5）：** GLOBAL。解除标准：“用户确认契约（已满足）；0A DDL 按契约重建，八字与六爻各 1 个端到端用例共用同一快照格式；R1 §5.14 旧 CHECK 与两版 yue_ling grep 无残留。”
3. **B3 解除前允许（§9.7）：** 非持久化准备；研究（结果不进入正式库）；资料整理；测试设计。
4. **B3 解除前禁止（§9.7）：** 正式数据库实施；正式数据写入；正式计算快照持久化；任何以“准备”“测试”为名、实际产生上述持久化结果的做法。
5. **§9.7 留待用户确认（原文）：** “这些验收动作能否在用完即弃、不进入正式发布链路的临时环境中执行并算作‘非持久化准备与测试’，本稿不自行认定……由用户在授权工程阶段时确认；确认前不执行。”
6. **原型（裁决 6、§11.3、W-12）：** 技术栈冻结前，在独立临时仓库做原型实测；结果只用于选型，原型代码不进入正式仓库；启动前须有用户授权与书面量化阈值。
7. **技术栈（§11.4）：** 未冻结；候选 React + TypeScript + Capacitor，备选 SwiftUI + GRDB。
8. **独立性（B4-11）：** 生成基准的实现必须独立于被测引擎；比对（Diff）不得由被测引擎自身执行。
9. **B2 与 N-6（原文）：**
   - §9.5 B2 解除标准：“无 zi_rule 的命盘不得持久为快照；第一版：锁定值 ye_zi_b 的端到端用例全部通过（含 23:30 立春前夜年月柱用例与 23:59→00:00 跨日用例），且 zi_zheng、zi_chu、ye_zi_c 三值在库层与引擎层被拦截的负面用例全部通过；后续开放多流派时恢复‘4 个取值各至少 1 个端到端用例’（【用户裁决 N-6】）。”
   - §13.9 N-6 裁决栏：“【用户裁决 N-6】2026-11-20：CFG-01 仍计入 8 项无默认值；第一版注册表状态 VERSION_LOCKED（锁定 ye_zi_b），value_source = version_locked，UI 公示；ye_zi_b 证据状态仍为推断，不升级；B2 改为锁定值正向用例加其余三值拦截用例。……”

## 二、授权范围（允许）

1. 新建私有仓库与 CI（GitHub Actions），工具版本锁定、构建可复现。
2. 实现**纯计算核心**（定义见 D2）：时间归一、节气查表、日柱、年月时柱、子时锁定规则、真太阳时、降级与按柱候选、六爻纯计算部分。
3. 按契约写 DDL，只在测试进程内存中临时建库（边界见 D1）。
4. 用已冻结的 B1、B4 数据做非正式工程测试与回归测试。
5. 在独立临时仓库做 §11.3 原型实测（阈值定稿后才开始，见 D5）。

## 三、禁止

1. 正式数据库实施：不建 formal.sqlite / user.sqlite 正式库文件，不纳入任何发布链路。
2. 正式数据写入：不写任何 FORMAL 对象、ApprovalRecord、AdmissionRecord。
3. 正式计算快照持久化。
4. 不发布 App，不构建面向用户的正式安装包（原型实测测试包除外）。
5. 不自动解除任何阻断；每项单独验收、由用户确认。
6. 引擎仓库不得引用、复制或修改 xuanshu-data 中的生成脚本与冻结基准（B4-11）；引擎只读取冻结数据文件并校验哈希。
7. 引擎第一阶段不联网、不接任何 AI 服务（裁决 5、W-13）。

## 四、需要用户定稿的事项

### D1　§9.7 的确认：临时内存库（建议：同意，附边界）
> 建议裁决文字：W-04 所需的“DDL 按契约重建”与“八字、六爻端到端用例”，可在用完即弃的临时环境中执行，算作非持久化准备与测试。边界：
> 1. 临时数据库只能在测试进程内存中创建（SQLite `:memory:`），测试结束即销毁；不得使用临时磁盘数据库、WAL 文件或任何落盘模式。
> 2. 测试数据、CalculationSnapshot、FORMAL 对象、ApprovalRecord、AdmissionRecord 均不得写入正式库、用户库或发布包。
> 3. 可以保存测试报告、日志与非业务测试向量；不得把测试快照、测试数据库作为可供 App 使用的数据资产。
> 4. 某项测试若必须落盘才能完成，先暂停该项，单独提交用户批准，不得自行扩大本授权。
>
> 根本边界：允许验证结构和行为，不允许借测试之名建立可供正式产品使用的持久化数据系统。

### D2　原型与引擎并行（建议：(b)，限定范围）
> 建议裁决文字：引擎纯计算核心与 §11.3 原型并行推进。E1 只写纯计算核心、单元测试与语言无关的 JSON 测试向量；不得引入 React、SwiftUI、Capacitor、SQLite 驱动、UI 状态管理或任何平台专属 API。E1 所用语言不视为最终技术栈已冻结；原型选型结果出来后，再决定引擎直接接入、适配还是重写。JSON 测试向量可跨语言复用，但不自动保证不同语言在日期、时区、浮点与边界行为上一致，须附明确的输入输出规范，并以实际测试结果为准。

### D3　纯计算核心的实施语言（建议：TypeScript，仅限当前阶段）
> 建议裁决文字：当前阶段以 TypeScript 作为纯计算核心的实施语言，不等于冻结最终技术栈。最终选 React + TypeScript 时，评估直接接入；最终选 SwiftUI 时，优先评估按同一套测试向量用 Swift 重写，是否采用 JavaScriptCore 须经独立原型验证后再定。不得为保留现有 TypeScript 实现而反过来影响技术栈选择。

### D4　仓库划分与跨仓库比对（建议）

| 仓库 | 内容 |
| --- | --- |
| `xuanshu-data`（已有） | 契约、冻结数据、生成脚本、数据核对 CI；新增 `harness/` 比对程序 |
| `xuanshu-engine`（新建，私有） | 纯计算核心、单元测试、测试向量、引擎 CI |
| `xuanshu-proto`（新建，私有，临时） | §11.3 原型实测代码与记录；选型结束后归档，代码不进引擎仓库 |

> 比对规则：
> 1. `xuanshu-engine` 只生成测试输出，不判断自身是否通过基准。
> 2. `xuanshu-data/harness/` 独立执行比对，不导入、不调用引擎内部任何代码。
> 3. 每次比对记录：引擎 commit、各冻结数据文件 SHA256、测试向量版本、比对程序 commit。
> 4. 结果文件由引擎 CI 产出并附上述版本信息；比对程序只接受版本信息齐全、与指定引擎 commit 一致的结果文件，拒绝混比。
> 5. 引擎不得修改 xuanshu-data 的冻结基准或生成脚本。

## 五、阶段与验收

| 阶段 | 内容 | 验收目标 |
| --- | --- | --- |
| E0 环境与基线 | 建 `xuanshu-engine`，锁定工具链，CI；W-01 grep 禁令、无网络与无 AI 依赖检查从第一天就在 CI 里跑 | CI 可复现，基础检查通过 |
| E1 纯计算核心 | 时间归一、节气、日柱、年月时柱、子时规则、真太阳时、降级与歧义候选、六爻纯计算部分；JSON 测试向量与输入输出规范 | 单元测试全过；核心不依赖 UI 与数据库 |
| E2 数据库结构准备 | 按契约写 DDL（D1 内存临时库）、快照格式、库层约束（含 zi_rule 拦截）、八字与六爻端到端用例 | W-04 所需结构与用例可执行；不产生任何持久化业务数据 |
| E3 独立回归与验收 | `xuanshu-data/harness/` 执行 W-05（B1）、B4 group 0～4、W-03（B2，库层与引擎层），以及具备前置条件的 W-01、W-02、W-07、W-09、W-13；B3 另须验收 **R1 §5.14 旧 CHECK 与两版 yue_ling grep 无残留**（B3 原始解除标准） | 有冻结基准的比对零差异，其余按各自契约断言；交 GPT 综合验收；用户分别决定是否解除 B1、B2、B4、B3 |
| P 原型 | `xuanshu-proto` 按定稿的 D5 实测两套技术栈；与 E1～E3 并行，但须等 D5 定稿 | 达到阈值；用户据此冻结技术栈 |

**验收规则：**
1. **有冻结基准的确定性比对，零差异是通过条件**（节气、日柱、均时差等对照冻结文件的比对）；其他测试按各自的契约断言验收，不一概理解为数据 Diff。出现差异时，先查明根因（引擎错误、基准错误、契约遗漏或精度定义问题），再提交用户裁决；“用户逐条批准差异”不是默认的通过路径。
2. **证据在先，报告在后。** 每个阶段至少保留：实际执行的命令与测试范围；引擎 commit、冻结数据版本与 SHA256；测试总数、通过数、失败数；差异明细与根因；是否触及任何持久化或发布边界。是否通过依据可复现的测试结果与契约标准，报告只用于定位问题。
3. 每个阶段结束交 GPT 验收，再由用户决定；任何阻断都不因阶段完成而自动解除。
