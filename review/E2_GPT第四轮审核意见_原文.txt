R1 剩余问题：U20 中的 token 并不保密

第 3.6 节第 (2) 条和第 (7) 条目前仍然依赖一个说法：

任何代码都能写入 U20，但写入者不知道闭包中的 txn_token。

问题在于，txn_token 本身就存放在主库表 U20 deletion_txn_marker 中。任何能够对该连接执行 SQL 查询的代码，都可以读取它。

因此，不能把“写入者不知道 token”作为防止伪造授权的依据。GitHub +1

这里需要区分两件事：

* 真正有效的保护： G/W 授权状态保存在 JS 闭包中；没有对应的 armed 状态，即使拿到正确 token，也不能通过授权函数。
* 不成立的保护： U20 中的 token 对其他 SQL 调用者保密。

这不意味着要推翻 U20 或重新设计删除架构。只需要修正安全论证，并补一个测试。

建议修改：

* 删除“写入者不知道闭包中的 txn_token”这一表述。
* 明确 U20 中的 token 对 SQL 调用者可见，不将其视为秘密凭证。
* 明确授权依赖闭包中的 G/W 状态、事务状态及完整参数匹配。
* 增加测试：在 G/W 均未授权时，测试代码先读取 U20 中真实的 token、audit_id、grant_seq，再直接调用授权函数并尝试删除、插入审计；所有操作仍必须被拒绝。
* 保留 G/W 互斥、同步调用、事务包装和静态检查。

这样才能证明实际安全边界，而不是依赖一个不存在的保密条件。
