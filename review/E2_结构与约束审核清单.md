## 1 结论摘要

1. **结构问题由 31 项增至 42 项。**
   - P-32～P-37 按 ChatGPT 要求新增。
   - P-38～P-42 是本轮复查新发现。
   - 根因由 5 条增至 7 条：新增“阻断与准入没有落到子项与步骤”（R6）、“结果范围与‘实际使用’没有定义”（R7）。
2. **端到端用例的状态改为逐子项推导，不再预设。**
   - 两个用例各跑三个治理场景：G0 真实映射、G1 契约裁决映射、G2 合成全满足，分别产出 BLOCKED、NON_FORMAL、FORMAL。
   - 推导表见第 7 节。
3. **推导中发现三处契约层冲突，须用户裁决：**
   - **年柱公式：** 年柱用公式“立春年 − 4 取 60 余数”。若按 BLK-6“年/日干支公式落库”与 K-3 的字面意思归入公式路径，则 BLOCKED-FORMAL，八字快照在 B4 解除前根本生成不了，W-04 的八字用例与 B3 互相卡住（P-41、Q-14）。
   - **七元组与暂缓拦截：** 八字七元组含暂缓子项 P-A-04 的参数 CFG-04。这与暂缓规则“写入配置时库层拒绝”（A-5，§7.5）正面冲突（P-21、Q-12）。
   - **六爻月建：** 契约 P-B-07 已写明“月建以节气换月，非农历初一”。第 1 版说“月建取法契约未写”是我漏读，M4-2 已收窄为只查交节时刻、交节当日的取法（第 9 节）。
4. **日柱、日辰都走 P-D-04 锚点递推。** 该路径按 N-10“暂按”口径不得作正式计算（附录“N-10”条、裁决 4）。因此在真实阻断状态下，八字与六爻快照最好也只能是 NON_FORMAL。这是推导结果，不是预设。
5. **删除入口改为连接级控制。** 授权状态保存在删除模块持有的自定义 SQL 函数闭包中，不保存在任何 SQL 可见、可伪造的数据里；TEMP 表方案作废。自定义函数在本进程内仍可被同名覆盖，属 ENG.1“只防程序错误”的限度，如实写明（P-35）。
6. **待裁决由 13 项增至 17 项（Q-1～Q-17）；Muse 项仍为 2 项（M4-1、M4-2 收窄）。**

## 3 通用库层规范（第 4 节各表共同遵守）

### 3.1 命名与失败定位

- 每个 CHECK 写成具名约束 `CONSTRAINT "<约束编号>" CHECK (...)`。SQLite 报错信息为 `CHECK constraint failed: <约束编号>`，可直接定位到第 5 节的测试编号。
- 每个触发器的报错写成 `RAISE(ABORT, '[<约束编号>] <说明>')`。
- NOT NULL 报错为 `NOT NULL constraint failed: <表>.<列>`，按表、列定位。
- 外键报错不带列名。每个外键单独一个负面用例；用例结束跑 `PRAGMA foreign_key_check`，返回表、行号、父表定位。
- 验证查询每条带编号，返回违规行的主键。

### 3.2 NULL 与 CHECK（P-33）

1. 强度“必须”的列一律 NOT NULL。
2. 可空枚举写 `col IS NULL OR col IN (...)`。
3. 条件必须写 `NOT (<条件>) OR col IS NOT NULL`，且 <条件> 中引用的列必须 NOT NULL，或写成 IS、COALESCE 形式，保证条件只取真或假。
4. 布尔列为 INTEGER NOT NULL CHECK (col IN (0, 1))。
5. 全部表 STRICT。
6. 校验方式：第 5 节 DB-N 矩阵对规格表中每个必填列做 NULL 插入；DB-E 矩阵对每个枚举列做越界与 NULL 插入。规格表由本清单第 4 节生成，不从 DDL 反推，避免自证。

### 3.3 历史表与序号（P-32；Q-5 建议，待裁决）

适用表：evidence_status_history、admission_record、formal_status_history、approval_record、component_default、blocker_change、branch_status_history。

1. **权威来源：** 历史行是唯一权威来源；当前值只由视图给出，不建可写的当前状态列。
2. **全表唯一、严格递增：** sequence_no 全表唯一、严格递增（触发器：新值 > 全表最大值）；允许断号，不允许重复与倒序。
3. **按键衔接：**
   - 每个键（例如 component_id + purpose）的首条记录 previous 为空；
   - 之后每条的 previous 必须等于同键上一条的 new（触发器）。
4. **数据版本不倒退：** data_release 取自 data_release 表，该表带整数 release_seq；同一键的新记录 release_seq 不得小于上一条。
5. **跨数据版本：** sequence_no 跨数据版本延续，不重置。由 CI 对比上一版检查，E2 不涉及跨版本。
6. **不可改删：** 一律拒绝 UPDATE 与 DELETE。

### 3.4 只读与只追加

- 正式库全部表拒绝 UPDATE 与 DELETE。
- 用户库计算层（输入、配置内容、配置取值、快照及其子表）拒绝 UPDATE。
- 用户库计算层的 DELETE 只放行第 3.6 节的删除入口。
- Branch 主行允许删除入口内置空 base_snapshot_id（§10.2），其余 UPDATE 拒绝。

### 3.5 快照封存协议（P-34 (a)）

1. 一个事务内写入顺序：
   - 先写 execution_trace_step、snapshot_dependency、snapshot_non_formal_reason、snapshot_degradation_reason、snapshot_resolved_context、snapshot_gov_*；
   - 最后写 calculation_snapshot。
   - 子表到快照的外键设为 DEFERRABLE INITIALLY DEFERRED，在提交时检查。
2. 快照行 BEFORE INSERT 触发器校验：
   - 依赖行至少覆盖 engine 一类；
   - NON_FORMAL 有原因行，FORMAL 无原因行；
   - 降级原因与 result_completeness 一致；
   - 轨迹覆盖该模块全部步骤编号；
   - FORMAL 快照的依赖中无个人对象。
3. 子表 BEFORE INSERT 触发器：所指快照已存在即拒绝，即封存后不可追加。
4. 任一步失败，整体回滚，不留孤儿子行。DB-R 组测试验证。

### 3.6 删除入口：连接级控制（P-35；Q-13 建议，待 GPT 审查）

**组成：**

1. **授权函数：** 删除模块在连接建立时注册自定义 SQL 函数 `xs_del_gate(profile_id)` 与 `xs_del_audit()`，均不设 directOnly，以便触发器调用。授权状态（被授权的 profile_id、本次审计 ID、所属事务标记）只保存在删除模块的 JS 闭包里，SQL 无法读写。
   - 未授权时，`xs_del_gate` 对任何参数返回 0。
   - 删除入口内，模块先“授权某档案”，事务结束（提交或回滚）时在 finally 中撤销。
2. **owner_profile_id 下放：** 用户库计算层每张表都带 owner_profile_id。插入时由触发器核对它与父行一致，使删除触发器无需跨表反查。
3. **删除触发器：** 每张受保护表 BEFORE DELETE：

   ```
   xs_del_gate(OLD.owner_profile_id) = 1
   AND EXISTS (SELECT 1 FROM deletion_audit WHERE audit_id = xs_del_audit())
   ```

   不满足即 RAISE。连接上没有注册该函数时，触发器执行报“no such function”，删除同样失败。
4. **删除入口流程：**
   - `BEGIN IMMEDIATE`；
   - 写审计行，审计 ID 交给闭包；
   - 授权该档案；
   - 按子到父顺序删除级联范围；
   - 回收无引用的配置（P-23）；
   - 置空 Branch.base_snapshot_id，并追加分支说明；
   - 提交；
   - finally 撤销授权。
5. **静态检查：** CI 中，注册 `xs_del_gate` 与 `xs_del_audit` 的代码只允许出现在删除模块一个文件里，并禁止 `DROP TRIGGER`、`PRAGMA writable_schema` 出现在非 DDL 文件中。
6. **限度：** 本进程内的代码仍可注册同名函数或删除触发器。这与契约 §1.2“只能发现篡改，不能阻止篡改”、ENG.1“只能防程序错误”一致，不承诺更多。TEMP 表不作任何授权依据。

### 3.9 结构化 JSON 字段（Q-9 建议，待裁决）

**适用列：** applicable_scope、scope、conditions、raw_payload、normalized_payload、result_payload。每列一律：

1. NOT NULL；
2. `json_valid(col)`；
3. 顶层为对象；
4. 带整数 `"v"` 结构版本；
5. 按版本校验必需键与类型（`json_type`）；
6. 未知键被拒（触发器以 json_each 比对白名单）；
7. 存储文本必须等于其规范化形式（第 6.2 节）——库层无法重算规范化，由封存前引擎校验，测试复核。

**范围（scope v1）：** `{"v":1,"kind":"all"}` 一种。

- ComponentDefault、variant_supersedes、param_variant_map 在同一子项、同一数据版本下以唯一约束保证只有一个 kind = all 的有效行。
- 其他 kind 一律被拒。
- 即重叠检测实现前不允许任何分段范围，也就不可能重叠。

**条件（conditions v1）：** `{"v":1,"all":[{"op":"param_selected","param":"CFG-01"}, …]}`。op 只许 param_selected、param_equals（param_equals 另带 value）。

## 5 约束验证清单

每条给出四项：正向输入（应成功）、反向输入（应失败或被查出）、预期结果、失败定位（第 3.1 节约定的报错标记或查询编号）。“基准行”指该表一行全部字段合法的样例；反向输入只改所列字段。

### 5.1 生成矩阵（覆盖全部表）

**DB-N 必填列 NULL**

- 正向：基准行插入成功。
- 反向：规格表中每个“必”列各置 NULL 一次。
- 预期：每次报 `NOT NULL constraint failed: <表>.<列>`。
- 失败定位：未报错的表与列。

**DB-N2 双向核对**

- 规格表必填集合与 DDL 的 notnull 集合逐列比对。
- 预期：两集合相等。
- 失败定位：差集。

**DB-E 枚举越界**

- 正向：每个枚举列取每个合法值各一次。
- 反向：取越界值 'X'；可空枚举另取 NULL（应成功），必填枚举取 NULL（应被 DB-N 拦截）。
- 预期：越界报 `CHECK constraint failed: <约束编号>`。
- 失败定位：约束编号。

**DB-K 外键**

- 每张表测试前断言 `PRAGMA foreign_keys` = 1，未开即整组失败。
- 正向：引用存在的父行。
- 反向：每个外键单独指向不存在的父行。立即外键在语句处报 FOREIGN KEY constraint failed；延迟外键在提交处报。
- 预期：每例各报一次；全部结束后 `PRAGMA foreign_key_check` 返回 0 行。
- 失败定位：用例编号（一例一个外键）与 foreign_key_check 输出。

**DB-I 不可改删**

- 反向：
  - 正式库每表 UPDATE 一列、DELETE 一行；
  - 用户库计算层每表 UPDATE 一列、未授权 DELETE 一行。
- 预期：报 `[DB-I-<表>]`。
- 失败定位：表名。

### 6.2 规范化规则 jcs-1（Q-11 建议，待裁决）

1. **基础：** RFC 8785 JSON 规范化。
   - 输出 UTF-8，无多余空白；
   - 对象键按 UTF-16 码元升序；
   - 字符串只转义 `"`、`\` 与 U+0000～U+001F：\b \f \n \r \t 用简写，其余写 \u00xx 小写；
   - 其余字符原样输出（含 U+2028）。
2. **Unicode：** 不做任何归一化（F14）。孤立代理项拒绝。
3. **重复键：** 解析阶段拒绝。
4. **数值：**
   - 只允许整数，范围 ±(2^53 − 1)。
   - 非整数一律以十进制字符串表示，按字段固定刻度：经纬度 6 位小数；均时差秒 3 位小数（§9.4 B1-1）；度数 1 位小数（CFG-09）。
   - −0、NaN、Infinity 拒绝。
5. **null 与缺失：**
   - 契约明定为 null 的值（如三柱模式时柱 null，§13.3；luck_cycle.value null，§13.2）显式写 null；
   - 其余不适用的字段一律省略，不写 null；
   - 各载荷版本的结构表列明每个字段属哪一类。
6. **数组：**
   - 默认有序，顺序即语义（六爻自初爻起；candidates 按 §13.3 固定规则，前一侧在先）；
   - 语义为集合的数组按规范化文本升序排列，未排序即拒。
7. **时间：**
   - 瞬时用 RFC 3339 UTC 字符串，毫秒精度：`YYYY-MM-DDTHH:MM:SS.sssZ`；
   - 民用时间另存原文字符串与 UTC 偏移秒数。
8. **哈希：** sha256，取规范化文本的 UTF-8 字节，输出 64 位小写十六进制。
9. **版本兼容（P-37）：**
   - 规范化版本只增不改，登记在 F06，每版冻结金标向量与其 sha256；
   - 每个哈希记录自身的 canonicalization_version；
   - 校验时按记录上的版本选用对应实现；
   - 旧版本实现永久保留在引擎中；
   - 不得用新版本重算旧记录来判定一致与否；
   - 新版本只用于新记录。
