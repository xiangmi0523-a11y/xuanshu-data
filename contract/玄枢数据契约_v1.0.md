### 0.3 六项架构裁决（已定，不再讨论）

## 1 数据模型总览与双库架构

契约把数据分成两个库：只读的正式库随数据版本发布，可写的用户库只放个人数据；正式对象永远不引用个人对象。

### 1.1 总原则

1. 规则、规则版本、文献证据分离存放；规则不等于引文，引文不等于结论。
2. 必选参数禁止静默默认；缺参返回 BLOCKED，不生成快照。
3. 计算快照不可修改、不可被重算覆盖；用户明确删除时可整体删除（【裁决 2】，替代旧稿“快照不可删除”）。
4. 非正式状态不得被 UI、导出或派生数据洗成正式；非正式沿依赖自动继承。
5. 治理历史（批准、撤销、证据状态、准入状态、阻断变更）只追加，永久保留。
6. 先原则后功能：未通过契约的模块不进入实现。

### 1.2 两个库（【工程方案】，来自工程可行性审查）

| 库 | 内容 | 写入方 | 关键约束 |
| --- | --- | --- | --- |
| formal.sqlite（正式库） | Source、Edition、Passage、Variant、Evidence、Rule、RuleComponent、RuleVariant、ParameterRegistry、engine\_release、ApprovalRecord、阻断表、状态历史 | 只由仓库内 YAML/CSV 经 CI 构建，随数据版本发布；按版本存为 formal\_v1.sqlite、formal\_v2.sqlite 等独立只读文件，保留策略见 §13.6（【用户裁决 G-5】） | App 只读；数据版本号对应一次提交；CI 对比上一版做只追加检查 |
| user.sqlite（用户库） | CalculationInput、CalculationConfig、CalculationSnapshot、SnapshotDependency、Branch 及个人研究对象、派生数据、最小删除审计 | App 本地写入 | 输入/配置/快照/依赖禁止 UPDATE；只允许“整体删除”这一条 DELETE 路径（§10） |

- **跨库引用：** 一律用三元组（数据版本号、稳定 ID、内容哈希），不用外键。
- **ID：** 机器 ID 用 UUIDv7，另设人读稳定 ID（如 P-D-05、CFG-01）；人读 ID 一经使用不改不复用。
- **哈希：** 规范化序列化后计算，并存 hash\_algorithm 与 canonicalization\_version。古籍原文保留原始 CJK 码位，不做 Unicode 归一化（F14）。
- **防篡改的限度：** 本地设备上的哈希链只能发现篡改，不能阻止篡改；契约不承诺更多。

## 2 文献与证据对象

文献层只记录“哪本书、哪个版本、哪一段写了什么”，证据层记录“这段文字能支持哪条规则到什么程度”；两层不混写。

### 2.3 Chapter、Passage、Variant、annotation

- **Passage：** 存原始码位原文及定位（Edition + 章 + 段），并建 FTS5 trigram 索引供本地检索。
- **Variant（异文）【工程方案】：** passage\_a 与 passage\_b 各自写明所属 Edition；增删类异文允许一侧为空；影响计算的异文必须关联受影响的 RuleComponent。variant.type 取自可扩展的 variant\_type 注册表，每个类型写明适用对象域（applies\_to\_domain）；Muse 的 7 类（字词/章序/章名/整句改写/注文有无/脱漏补录/术语别名）只登记为“古籍文本异文”域的类型，不得全库通用，其他对象域（如规则算法、表数据）需要时另行登记新类型，类型码稳定，旧类型码不删除、不改义【用户裁决 A-10；架构验收 3.6】。
- **annotation：** 必须指向被注的 Passage；层级（经文/原注/任注/徐注…）用可扩展的注册表，不写死枚举。
- **《滴天髓》基线【Muse】：** 著录项 15 个（不是 5 个）；62/63/64 章并存；异文 27 条 YW-01～YW-27，均不改变干支计算，仅 YW-09、YW-18 改变措辞；42 论本不是摘要本：A 级引文为零，最高 B；两条底本链均为推断。展示依 CFG-16 选版本。

### 2.5 evidence\_link 与 evidence\_review

- **evidence\_link：** Evidence ↔ RuleComponent（而非只到 Rule），带 branch\_id。个人证据即使链到正式子项，正式判定时一律不计入。
- **evidence\_review：** Muse/ChatGPT 的审查意见单独存放，不写入 ApprovalRecord（【裁决 1】）。

## 4 证据准入政策与状态推导

一个子项能否进入正式计算，由三个独立维度决定：证据状态、准入状态、正式状态；三者各有自己的只追加历史，不互相覆盖。

### 4.1 证据层级的权限（【Muse】§2.3）

| 层级 | 正式计算 | 原文栏 A 级 | 研究用途 |
| --- | --- | --- | --- |
| E1 一手原典 | 可 | 可 | 可 |
| E2 可靠版本交叉核对（两个独立来源） | 可 | 不可（B 级标注展示） | 可 |
| E3 二手转录 | 不可 | 不可 | 可，NON\_FORMAL |
| E4 推断 | 核心子项 BLOCKED，附带子项 NON\_FORMAL | 不可 | 可，须写模型前提 |
| E5 未知 | BLOCKED | 不可 | 仅登记缺口 |

完整九行映射见附录 E-MAP。要点：同一转录链上的两个本子不算交叉核对；三源摘要一致但未读原文，最多 SINGLE\_SOURCE、B 级、不得正式计算（【用户裁决 K-1】：摘要互见不算交叉核对）。

### 4.3 聚合规则

【用户裁决 A-7；架构验收 3.10】证据等级（evidence\_tier）、证据状态（evidence\_status）、主张状态（claim\_status）分维度各自聚合，不得合并成单一等级再聚合。(1) evidence\_tier：取有效正式证据中最低的等级；REJECTED 的证据不参与有效证据聚合。(2) evidence\_status：保守聚合；任一证据为 UNVERIFIED 或 DISPUTED，聚合结果不得高于 CROSS\_CHECKED；全部证据均为 REJECTED 时不得产生有效支持状态。(3) claim\_status：不按线性等级聚合；Rule 层展示各 RuleComponent 的主张状态集合，状态混合时显示 MIXED，并保留子项明细。聚合值只用于展示和准入核查，不自动改变 AdmissionRecord 或正式状态，也不自动升级任何状态。个人证据（branch\_id 非空）不参与正式聚合。迁移数据的处理见 §4.6：不再把“已证实”默认映射为 CROSS\_CHECKED。

### 4.4 三条独立历史【工程方案】

| 历史表 | 记录对象 | 状态枚举 | 写入方式 |
| --- | --- | --- | --- |
| evidence\_status\_history | Evidence（evidence\_status）；RuleComponent（claim\_status） | evidence\_status 六档、claim\_status 四档，分列记录，不合并 | 只追加，随正式数据版本发布 |
| admission\_history（AdmissionRecord） | RuleComponent × 用途（计算/原文/定性） | 五档 admission\_status | 只追加；是准入历史的唯一依据（【用户裁决 A-6】） |
| formal\_status\_history | Source、Edition、Evidence、RuleVariant | FORMAL / NON\_FORMAL | 只追加 |

AdmissionRecord 必须字段：admission\_id、component\_id、purpose（固定为 calc / text / qualitative 三值）、previous\_status、new\_status、conditions（结构化条件，如“CFG-01 已选”，原 RuleComponent.condition\_spec；new\_status 为 CONDITIONAL 时必填）、依据（证据或裁决引用）、data\_release、sequence\_no、decided\_by（仅用户）。AdmissionRecord 只追加；某子项某用途的当前准入 = component\_id + purpose 下 sequence\_no 最新的一条，不另存可直接修改的当前准入状态【架构验收 3.3】。

### 4.5 计算准入的映射（第三轮工程审查）

为避免与 formal\_status 重名，计算侧准入改名为 CALC\_FORMAL / CALC\_RESEARCH / CALC\_BLOCKED：

| admission\_calc | 得到 |
| --- | --- |
| FORMAL\_ALLOWED | CALC\_FORMAL |
| CONDITIONAL，条件已满足 | CALC\_FORMAL |
| CONDITIONAL，条件未满足 | CALC\_BLOCKED |
| RESEARCH\_ONLY | CALC\_RESEARCH |
| DEFERRED | CALC\_BLOCKED |
| PROHIBITED | CALC\_BLOCKED |

待裁决、证据不足、已证伪、永久不准入在数据上分别表达（【裁决 4】）：待裁决是 Dispute 未裁决，证据不足是 evidence\_status，已证伪是 claim\_status，永久不准入是 PROHIBITED。

### 4.6 证据等级、证据状态与主张状态分离（【用户裁决 A-7、A-8】，结构修正 S-5）

三者是三个独立维度，各自取值、各自追加历史，不互相推出：

- **evidence\_tier（证据等级 E1–E5）：** 来源层级，一手原典、可靠版本交叉核对、二手转录、推断、未知（§4.1）。
- **evidence\_status（证据状态）：** 这条证据核到哪一步，六档 UNVERIFIED / SINGLE\_SOURCE / CROSS\_CHECKED / PRIMARY\_VERIFIED / DISPUTED / REJECTED（§2.4）。
- **claim\_status（主张状态）：** 对子项所主张内容本身的判断：已证实 / 推断 / 未知 / 已证伪。

1. 不得把旧数据的“已证实”直接映射为 CROSS\_CHECKED 或任何 evidence\_status。迁移时 claim\_status 原样带入；evidence\_tier 与 evidence\_status 按实际可见资料逐条判定。
2. 来源不明的条目一律 evidence\_status = UNVERIFIED，并填写 missing\_evidence 与 next\_source；不因“已证实”字样、引用次数或时间推移自动升级，升级只能通过新的 evidence\_status\_history 记录写入，并随正式数据版本发布。
3. C-A 的 A 级限制只作用于 is\_calendar\_anchor 为“是”的历法锚点子项。其他历法辅助子项（显示、换算、查表等）按 §4.1 与 E-MAP 的通用规则处理，不套用 A 级限制。
4. 具体哪些子项是历法锚点，以正式数据中的锚点清单为准；清单属于第一次正式数据发布前的数据工作，不是契约结构问题【工程方案】。

CFG-16 只在 R2 第 3 章 §5.3 定义，不在第 8 章 §5 表内；本稿将其并入统一 ParameterRegistry，registry\_origin 记为补充来源登记，计入 8 项无默认值【架构验收 3.1】。统一注册表实际包含 20 项：19 项为原有注册参数，CFG-16 为补充来源登记项。CFG-17（滴天髓层级，默认 jingwen+yuanzhu）不计入 20 项，是否入注册表【待裁决，可后置】，不擅自纳入。

### 5.3 “暂按”参数的处理（【裁决 4】）

- 任何带“暂用 / 暂按 / 待裁决”的取值不得用于正式计算，也不因有了暂定值而变正式。
- 可执行且允许研究：生成 NON\_FORMAL 快照，non\_formal\_reasons 写明“参数 X 待裁决”。
- 缺参、缺选择、缺条件：BLOCKED，不生成快照。
- 适用范围：CFG-05、CFG-05W、CFG-04 取值集（D-03 双表冲突）、CFG-01 “暂用 zi\_zheng”、siling\_day\_count 默认强度。具体见配套清单第 6 节。

### 5.4 CalculationConfig（工程问题 14）

旧稿只存八字七元组，六爻、风水、历法的参数无处可存。修订为：配置存**本次计算实际用到的全部参数**，每项带取值来源。

| 字段 | 强度 | 说明 |
| --- | --- | --- |
| config\_id | 必须 | 配置系列的稳定 ID |
| config\_version | 必须 | 同一 config\_id 内单调递增；(config\_id, config\_version) 一经写入不可修改 |
| config\_hash | 必须 | 对 module、全部 param\_values（含 value\_source）、registry\_version 与规范化/序列化版本的规范化序列取哈希（与下文配置版本规则一致）；内容相同则哈希相同 |
| module | 必须 | 所属模块 |
| param\_values（连接表） | 必须 | 挂在 (config\_id, config\_version) 下，每行：param\_id、取值、value\_source（user\_selected / approved\_default / follows\_param / version\_locked；version\_locked 只用于注册表状态为 VERSION\_LOCKED 的参数，第一版仅 CFG-01，【用户裁决 N-6】） |
| registry\_version | 必须 | 取值当时的注册表版本 |
| branch\_id | 条件必须 | 由依赖闭包推导，不手填【Muse】 |

八字七元组（zi\_rule、zi\_reference\_time、yue\_ling\_version、siling\_day\_count、hidden\_stems\_version、shen\_wu\_ji、hidden\_stems\_weight\_scheme）仍是八字配置的最小集合，不再是全部。全局默认改动不重算已存命盘；用户切换参数时生成新快照并高亮四柱/十神/格局/司令干差异，不静默重算。

**配置版本规则（【用户裁决 A-3；架构验收 3.2】，结构修正 S-3）：** CalculationConfig 不可变，有三个标识：config\_id 为配置系列的稳定标识；config\_version 为同一系列内单调递增的不可变版本；config\_hash 为规范化配置内容的哈希，至少覆盖模块、全部参数取值、value\_source、registry\_version 与规范化/序列化版本。任何参数、取值来源或注册表版本变化，都写一条新的 config\_version（同一系列）或新的 config\_id（新系列），旧行不改不删；内容与已存版本完全相同时复用该版本，不新建。CalculationSnapshot 必须同时引用 config\_id、config\_version 与 config\_hash（§6.2），读取时校验三者一致。原“不可变行 / 物化取值”二选一按不可变行定案。

## 6 计算输入、快照、依赖与指纹

一次计算由四个不可变对象组成：输入（原始出生资料）、配置（全部参数取值）、快照（结果）、依赖（逐项用到的规则与数据版本）；快照有两组指纹，结果指纹只看“算出了什么”，治理上下文只看“当时的批准与阻断状态”。

### 6.1 CalculationInput（新增，工程问题 6）

| 字段 | 强度 | 说明 |
| --- | --- | --- |
| input\_id、input\_hash | 必须 | 输入行不可变 |
| domain | 必须 | BAZI / LIUYAO / FENGSHUI / CALENDAR（周易三层不并入一个域） |
| raw\_payload | 必须 | 出生证明钟表时间、出生时刻精度 time\_precision（MINUTE / SHICHEN / UNKNOWN）与性别 gender（MALE / FEMALE / UNKNOWN）（八字域均必填，【用户裁决 G-1、G-2】，§13.2、§13.3）、原始时区、经纬度、是否已含夏令时、地点名称；六爻为起卦时刻与方式；铜钱/揲蓍结果作为输入保存 |
| normalized\_payload | 必须 | 归一化后的值 + normalizer\_version |
| tz\_resolution（时间链第一步） | 条件必须 | 有出生时刻时必填：tz\_id、UTC 偏移秒数、DST 标记、tzdata 版本、时区表生成版本、偏移来源、确认记录、歧义原因（§11.1） |
| place\_ref | 条件必须 | 地点/坐标数据版本 + 条目 ID |
| owner\_profile\_id | 必须 | 指向个人档案，用于 §10 整体删除的级联 |

四柱等结果只存为派生快照，不得替代原始输入（R2 第 2 章 §5）。

### 6.2 三者的关联

Snapshot 同时引用 input\_id + input\_hash 与 config\_id + config\_version + config\_hash；一个输入可对应多个配置与多个快照；快照不直接挂分支，分支归属由配置推导（D 轨）。

### 6.3 CalculationSnapshot 字段

| 字段 | 强度 | 说明 |
| --- | --- | --- |
| snapshot\_id | 必须 | 不可复用 |
| input\_ref、config\_ref | 必须 | 见 §6.2 |
| engine\_release\_id | 必须 | 引擎名称 + 版本（§6.6） |
| result\_payload、result\_hash | 必须 | 结果内容与其哈希 |
| result\_fingerprint | 必须 | 见 §6.5 |
| governance\_context | 必须 | 见 §6.5 |
| formal\_status | 必须 | FORMAL / NON\_FORMAL，生成时推导并物化，事后不改 |
| research\_scope | 必须 | 由 formal\_status、branch\_id、non\_formal\_reason 等派生，生成时按计算当时的状态物化，事后不改（【用户裁决 A-2】，§7.4） |
| non\_formal\_reasons | 条件必须 | NON\_FORMAL 时必填，列表，每项指向触发它的 R-I 段与上游节点 |
| execution\_trace\_ref | 必须 | 指向逐步执行轨迹（§6.6） |

合法组合只有两种（第三轮工程审查）：AVAILABLE + CALC\_FORMAL + FORMAL；AVAILABLE + CALC\_RESEARCH + NON\_FORMAL。BLOCKED 不产生快照，只记一条审计事件；审计事件既不含计算结果，也不含个人可识别内容（【用户裁决 K-4】）。快照另存 resolved\_context 与 data\_fingerprint（【用户裁决 G-5】，§13.6），结果中另记 degradation\_reasons 与按柱候选（【用户裁决 G-1、G-2、G-3】，§13.1～§13.4）；降级与候选结果和上述两种合法组合的关系：降级结果可落为 FORMAL 快照，另记 result\_completeness（COMPLETE / OK\_WITH\_DEGRADATION）与 degradation\_reasons，二者与 formal\_status 正交；requires\_user\_confirmation = true 的候选未经用户确认不落任何快照，只存为 §9.1 的“未完成配置”草稿，确认后按 §9.3 生成快照（【用户裁决 N-1】）。

### 6.4 SnapshotDependency（工程问题 8）

每个快照逐项记录依赖，一行一项，而不是只存一个总哈希：

| dep\_type | 记录内容 |
| --- | --- |
| rule\_variant | rule\_variant\_id + version\_no + content\_hash + 计算当时的 current\_approval\_id |
| edition / evidence | ID + 版本 + 内容哈希 |
| parameter | param\_id + 取值 + value\_source + registry\_version |
| calendar\_data | 节气表版本、历法锚点版本、EoT 方案标识（含 frozen / eot\_degraded） |
| tz\_data | tzdata 版本（如 IANA 2026f）、时区表生成版本；无法取得记“未记录”，不得留空 |
| place\_data | 地点/坐标数据版本 |
| engine | engine\_release\_id、normalizer\_version、hash\_algorithm、canonicalization\_version |
| cross\_domain | 跨域引用（如风水 P-C-05 引用八字命卦快照）【D 轨 R-I-8】 |

### 6.5 结果指纹与治理上下文分离（工程问题 7）

| 组 | 成分 | 用途 |
| --- | --- | --- |
| result\_fingerprint | 输入哈希、配置哈希、每个用到的子项/变体内容哈希、数据版本、引擎版本、参数注册表版本、时区表生成版本、地点数据版本、节气数据版本、哈希算法与规范化版本 | 判断“同样条件是否得同样结果”；可重复性校验 |

### 6.6 引擎版本登记与执行轨迹（工程问题 13）

- **engine\_release：** engine\_release\_id、版本号、发布的数据版本、包含的计算函数清单（calc\_function\_id + 函数版本 + 实现哈希）。

- **执行轨迹：** 每步记录步骤号、所用 calc\_function\_id、输入摘要、输出摘要、该步的状态（完成 / 未执行·原因）。C-G 类必须能从轨迹读出“经度项已算、均时差待定、子时待选”。

## 7 个人研究分支与非正式继承

个人研究隔离是数据血缘问题，不是 UI 标注问题：是否非正式只由依赖闭包机械推导，人工只能改叶子标记。本节主体来自 D 轨：Branch 采用独立对象（【用户裁决 A-1】），research\_scope 派生（【用户裁决 A-2】），暂缓规则事前拦截（【用户裁决 A-5】）；其余字段与传播规则属【契约新设计】，经 ChatGPT 补充架构验收（2026-11-19）确认，已随 v1.0 获用户批准（2026-11-20）。

### 7.1 Branch 对象（独立对象，【用户裁决 A-1】，工程问题 3）

| 字段 | 强度 | 说明 |
| --- | --- | --- |
| branch\_id | 必须 | 不可复用；同名分支用不同 ID |
| branch\_name | 必须 | 仅展示 |
| parent\_branch\_id | 必须（可空） | 正式基线为空；不得悬空 |
| base\_data\_release | 必须 | 分支从哪个正式数据版本分出（D 轨称 base\_version）；任何分支都必须有，库层非空（【用户裁决 A-12】） |
| base\_snapshot\_id | 可选 | 分叉时的对照快照，用途仅为“分支前/后对照”；非必填（【用户裁决 A-12】） |
| owner | 必须 | 单人产品固定值，只用于审计 |
| status（历史表） | 必须 | active / promoted / merged / abandoned，只追加 |
| branch\_note | 可选 | 目的说明，不存规则内容 |

状态含义（第三轮审查指出 merged 未定义）：**promoted** = 分支内容已提交正式审查；**merged** = 对应内容已由某个正式数据版本以新对象发布，状态记录必须引用该数据版本号；**abandoned** = 废弃。merged / abandoned 的分支不再产生新配置或快照，不得复活。

D 轨备选方案 B（删去“分支”，改称“个人研究标记”）不采用（【用户裁决 A-1】）。

### 7.2 晋升路径（与只读正式库统一）

1. 个人内容不得通过把 formal\_status 从 NON\_FORMAL 改为 FORMAL 晋升；库层必须拒绝这种写入。
2. 晋升 = 用户导出分支内容 → 进入研究/审查流程 → 用户批准 → Claude 在仓库内建新正式对象（新 ID，带 promoted\_from\_branch\_id + promoted\_from\_id）→ 随下一个正式数据版本发布。手机端不做晋升（【裁决 1】）。
3. 原个人对象保持 NON\_FORMAL。

### 7.3 非正式传播规则 R-I-1～R-I-8（工程问题 11）

传播方向 = 从被依赖方到依赖方：Source → Edition → Evidence → RuleVariant → Config → Snapshot → 派生数据。展示、搜索、导出只读快照已物化的状态，不重新推导，不反向污染上游。

| 段 | 上游 → 下游 | 规则 |
| --- | --- | --- |
| R-I-1 | Source → Edition | Source 为 NON\_FORMAL，其 Edition 不得为 FORMAL |
| R-I-2 | Branch → RuleVariant / Edition / Variant | branch\_id 非空 ⇒ NON\_FORMAL + PERSONAL\_RESEARCH |
| R-I-3 | Edition → Evidence | Edition 为 NON\_FORMAL，引用它的 Evidence 不得为 FORMAL；证据核验状态不受影响（可以 PRIMARY\_VERIFIED 但 NON\_FORMAL） |
| R-I-4 | Evidence → RuleVariant | 支持性证据为 NON\_FORMAL ⇒ 变体不得为 FORMAL；反证/限定/异文记录不触发；evidence\_role 枚举须固定 |
| R-I-5 | RuleVariant / Edition / Variant → Config | 依赖闭包中任一 NON\_FORMAL 或 branch\_id 非空 ⇒ Config NON\_FORMAL；禁止手动改为 FORMAL，库层拒绝而非只记日志 |
| R-I-6 | Config → Snapshot | 快照生成时由配置推导并物化，事后不改 |
| R-I-7 | Snapshot → 派生数据 | 来源快照 NON\_FORMAL ⇒ 派生数据 NON\_FORMAL；以 derived\_from\_snapshot\_id + 指纹绑定 |
| R-I-8 | 跨域依赖 | 取各域最弱值；跨域引用必须显式登记，未登记不得参与计算 |

原 §7.3 触发情形 5“依赖链中任意上游对象为非正式”删去，改为“适用 R-I-1～R-I-8，审计须能指出触发段与上游节点”。个人证据链到正式子项时，正式判定不计入（§2.5）。

### 7.4 formal\_status 与 research\_scope 联动

【用户裁决 A-2】research\_scope 由 formal\_status + branch\_id + non\_formal\_reason 等派生，不独立输入：FORMAL + 空分支 = FORMAL；FORMAL + 非空分支 = 非法；NON\_FORMAL + 非空分支 = PERSONAL\_RESEARCH；NON\_FORMAL + 空分支时，原因为未核验/争议/阻断者属 FORMAL 范围内的非正式，原因为实验/个人校勘者属 PERSONAL\_RESEARCH。快照生成时按计算当时的状态物化 research\_scope，之后上游对象状态变化不回写旧快照。D 轨方案 B（两字段独立）不采用。

### 7.5 实验规则与暂缓规则

- 实验规则是 non\_formal\_reason = experiment 的 RuleVariant，必须填实验字段组（假设、状态、晋升路径、有效期）。
- P-B-10 暂缓期间不得以“实验规则”名义进入正式配置（D 轨 J-3）。
- **暂缓规则事前拦截（【用户裁决 A-5】）：** 暂缓规则的子项及其变体不出现在普通计算配置的选择列表中，写入配置时库层拒绝，不采用“先进入、事后降级”。只有当该子项“计算”用途的现行 AdmissionRecord 为 RESEARCH\_ONLY 时，才可在明确标为研究的路径中使用，结果一律 NON\_FORMAL，non\_formal\_reasons 写明“暂缓规则”；admission\_calc 为 DEFERRED 的子项在任何路径都是 BLOCKED-FORMAL。

## 8 批准、发布与治理记录

正式批准只随正式数据版本发布，只有用户能做最终批准；App 只读取批准状态，不能在本地批准、撤销或修改（【裁决 1】）。

### 8.1 发布链路

1. Muse 提交研究与证据建议 → 存为 ReviewRecord（role = research）。
2. ChatGPT 做架构审查 → 存为 ReviewRecord（role = architecture）。
3. 用户做最终批准或不批准 → 存为 ApprovalRecord。
4. Claude 按批准结果在仓库内改 YAML/CSV，由 CI 构建正式数据发布包（formal.sqlite + 发布清单），数据版本号对应提交。
5. App 更新数据版本后读取新状态；已存快照不重算。

任何一步的意见都不得代替第 3 步。Claude 不裁决规则批准。

### 8.2 ApprovalRecord（工程问题 4）

| 字段 | 强度 | 说明 |
| --- | --- | --- |
| approval\_id | 必须 | 稳定 ID |
| sequence\_no | 必须 | 全库单调递增，判定“最新一条”的唯一依据 |
| target\_type、target\_id | 必须 | 以 rule\_variant 为基本单位；不得以 Rule 批量批准其全部变体 |
| target\_content\_hash | 必须 | 被批准变体的 content\_hash；变体内容变化即失效 |
| data\_release | 必须 | 生效的正式数据版本号 |
| decision | 必须 | approve / approve\_conditional / reject / revoke |
| decided\_by | 必须 | 只能是用户；库层 CHECK |
| decided\_at | 必须 | 裁决时间 |
| basis\_refs | 必须 | Evidence ID + 报告章节精确位置 |
| review\_refs | 可选 | 指向 ReviewRecord（Muse/ChatGPT 意见） |
| scope | 必须 | 适用模块/版本范围 |
| conditions | 条件必须 | 附条件批准时必填，结构化 |
| supersedes\_approval\_id | 可选 | 指向被取代的记录 |
| revoke\_reason | 条件必须 | revoke 时必填：取自开放式撤销原因注册表（§8.4），可多选；旧原因码不删除 |

与 C 轨草案的两处差异：(1) C 轨 decided\_by 可为“用户 / ChatGPT”，本稿按【裁决 1】只留用户，ChatGPT 意见进 ReviewRecord；(2) C 轨让旧记录 status 原地改为“已撤销/已取代”，本稿不存可改的 status 列，当前状态按 sequence\_no 从记录链推导，符合只追加。

RuleVariant 的 FORMAL 当且仅当：存在现行有效的 approve 记录，其 target\_content\_hash 等于变体当前 content\_hash，且批准要件齐全。

### 8.3 批准要件（【Muse C 轨】E1-1～E1-7）

1. 证据等级已按 E-MAP 确定，不得升档。
2. 至少一条证据指向具体 Edition 与可复核定位；任何引文不得标“ctext 已核”（OP-01a）。
3. 所属规则归属已定；暂缓规则须先满足解封条件。
4. 依赖参数已有取值或强制选择流程；附条件须写明条件。
5. 不在未解除的阻止项覆盖范围内。
6. 异文类变体已定影响档（无影响 / 断语表述 / 计算影响），计算影响类须专项裁决。
7. 裁决记录完整。

附条件批准的条件不满足时视同未批准；条件满足后须新建确认记录，系统不得自动解释为生效（R-E4）。P-B-10 是实例：模拟已完成不等于批准完成。

### 8.4 撤销与旧快照（R-E1～R-E5）

- 撤销是一条新的 revoke 记录，只能随后续正式数据版本发布。
- 旧快照保持计算当时的全部字段，当时为 FORMAL 的仍是 FORMAL。
- 展示时用快照的 governance\_context 对照当前批准与阻断状态，不一致即在全部出口附警告。警告四要素：变体已撤销批准、撤销时间、撤销依据、重新计算建议。
- 警告不是快照状态，出现或消失都不改快照字段；复制、导出、重命名不得移除。
- 重算创建新快照；用户明确从旧快照发起时，新快照的 recomputed\_from\_snapshot\_id 指向旧快照（§6.3），旧快照不变、不失效。
- **撤销触发清单是开放式的（【用户裁决 A-13】，结构修正 S-6）：** 触发原因注册表至少含新证据、证据降级、原始版本失效、算法缺陷、参数变化、适用范围失效、依赖数据版本撤回；原 C 轨的“裁决变更”“阻止项新增”保留为条目。注册表可随正式数据版本新增条目，旧条目不删不改。触发只开启审查：写一条 ReviewRecord（role = revocation\_trigger，记录触发类型、目标对象、来源事件、时间与审查处置，【架构验收 3.7】），不改任何 ApprovalRecord，不改任何 formal\_status，也不在出口产生撤销警告。是否撤销仍须用户裁决；撤销 = 新的 revoke ApprovalRecord，随后续正式数据版本发布，之后才按上述各条处理旧快照的警告。

### 8.5 权威记录与 GovernanceRecord（工程问题 5）

每类治理事件只有一个权威来源：

| 事件 | 权威记录 |
| --- | --- |
| 批准/撤销 | ApprovalRecord |
| 审查意见 | ReviewRecord |
| 撤销触发（只开启审查） | ReviewRecord（role = revocation\_trigger）【架构验收 3.7】 |
| 证据状态、主张状态变更 | evidence\_status\_history（分列） |
| 准入状态变更 | AdmissionRecord |
| 默认变体变更 | ComponentDefault【架构验收 3.4】 |
| 阻断变更（启用/解除） | blocker\_change（须附用户裁决引用） |
| 争议裁决 | Dispute 的裁决记录 |

GovernanceRecord 不再是独立写入的记录，只是构建时由上述权威记录自动生成的索引，字段：来源表、来源记录 ID、对象、previous\_state、new\_state（固定枚举）、data\_release。索引与权威记录不一致时以权威记录为准，CI 须检出。

## 9 阻断与计算状态

每次计算只有三种结果：BLOCKED（不生成快照）、NON\_FORMAL（生成研究快照）、FORMAL（生成正式快照）；局部阻断只锁它自己的范围，不得无理由锁死全局。

### 9.1 三态与两类 BLOCKED（【Muse C 轨】）

| 状态 | 含义 | 快照 |
| --- | --- | --- |
| BLOCKED-HARD | 入口不存在：代码中无该计算函数、UI 无入口，不是“做了但禁用” | 无 |
| BLOCKED-FORMAL | 路径存在但本次正式计算被拒（如 CFG-01 未选）；可保存“未完成配置”，但不得伪装成已完成计算 | 无 |
| NON\_FORMAL | 路径可执行，证据、批准或研究条件不满足 | 研究快照，全出口带标记 |
| FORMAL | 全部条件满足 | 正式快照 |

“未完成配置”是用户库中一个独立的草稿对象，不是快照；它也属于§10 删除级联范围。为避免与 NON\_FORMAL 混淆，BLK-3/BLK-4 不得以“先做一个 NON\_FORMAL 的玄空排盘”顺代。

### 9.2 三级作用范围

| 范围 | 含义 | 当前成员 |
| --- | --- | --- |
| GLOBAL | 全局生效的门：B2 挡住无 zi\_rule 命盘的持久化；B3 挡住正式数据库实施、正式数据写入与正式计算快照持久化，不挡研究与非持久化准备（§9.7） | B2、B3 |
| MODULE | 挡住一个模块进入开发 | BLK-1～BLK-5 |
| PATH | 只挡住模块内一条子路径 | BLK-6、BLK-7、B1、B4 |

任何模块级或路径级阻断升为全局级，必须在注册表写明理由并经用户裁决，否则无效。七项中无一项是 GLOBAL。

### 9.3 判定顺序（工程问题 10）

纯函数在核心层按顺序判定，存储层写入前再核一次：

1. 模块或路径属于 BLOCKED-HARD → 不得调用，也不会有入口。
2. 缺输入（gender、time\_precision 取 UNKNOWN 或 SHICHEN 是显式取值，不算缺输入，按 §13 降级或给候选，【用户裁决 G-1、G-2】）、缺必选参数、争议变体未选、时区未确认、依赖 EoT 的路径缺步骤 → BLOCKED-FORMAL。
3. 子项 admission\_calc 得 CALC\_BLOCKED（DEFERRED、PROHIBITED、CONDITIONAL 未满足），或缺现行批准而不属 RESEARCH\_ONLY 路径 → BLOCKED-FORMAL（【用户裁决 K-2】）。
4. 任一子项 CALC\_RESEARCH、任一参数属“待裁决口径”、任一依赖 NON\_FORMAL、缺现行批准但属 RESEARCH\_ONLY 路径 → NON\_FORMAL（写明全部原因）。
5. 其余 → FORMAL。

“缺现行批准”的分流按【用户裁决 K-2】：除 RESEARCH\_ONLY 路径外，缺现行批准一律 BLOCKED-FORMAL（第 3 步）；只有 RESEARCH\_ONLY 路径可生成 NON\_FORMAL（第 4 步）。

## 10 个人资料删除

用户可以整体删除一份出生资料及其全部个人数据；删除后不留任何可识别的命盘，只留一条不含个人内容的删除审计（【裁决 2】，工程问题 12）。

### 10.1 替换旧表述

- v0.1.1 中“快照不可删除”类绝对表述，以及 D 轨 §1.10 与 C 轨 G.4 第 2 条“旧快照不得删除”的草案，统一改为：**快照不可修改、不可被重算覆盖；系统和重算流程不得删除快照；用户明确删除个人资料时，相关快照随之整体删除。**
- 四轨草案的“归档只改展示状态、不删记录”仍适用于普通归档；只有“删除个人资料”这一个操作可以真删。

### 10.2 删除单元与级联范围

删除单元 = 一个个人档案（owner\_profile\_id）。级联删除以下全部记录：

| 对象 | 删除方式 |
| --- | --- |
| 个人档案、CalculationInput（含原始与归一化输入、时区确认记录、地点） | 删行 |
| 引用这些输入的 CalculationConfig、未完成配置草稿 | 删行 |
| CalculationSnapshot、SnapshotDependency、执行轨迹 | 删行 |
| 派生数据：比较视图、差异高亮、导出记录、分享链接记录 | 删行；分享链接失效 |
| 缓存与全文索引中的对应条目（含 FTS 影子表） | 删除并重建索引段 |
| 引用这些快照的个人研究记录（笔记、Judgment、分支中的对照快照） | 删行；若一条记录同时引用多个档案，删去对当前档案的引用与任何可识别内容 |
| Branch.base\_snapshot\_id 指向被删快照 | 置空并追加一条分支状态说明（不含个人内容） |

不受影响：正式库全部内容（文献、规则、注册表、数据版本、批准记录）；不引用该档案的个人研究记录（个人校勘、实验规则）。

### 10.3 删除的工程条件【工程方案】

- 禁止 DELETE 的触发器保留，只给“删除个人资料”这一个入口开放：在同一事务内先写审计行，再删级联范围内的行；任何一行删不掉则整体回滚。
- 删除后执行 VACUUM（或同等操作），不让已删页留在数据库文件中；若使用 WAL，须同步处理。
- 哈希链中被删节点的位置以审计行占位，使链校验能区分“合法删除”与“篡改”。

### 10.4 最小删除审计

| 可以保留 | 不得保留 |
| --- | --- |
| 审计 ID、删除时间、删除对象类型与条数、触发方式（用户操作）、App 版本与数据版本、是否完整成功 | 姓名、出生信息、地点、快照内容、任何个人记录的 ID 与哈希、任何能反推个人数据的值 |

哈希也在禁存之列：出生资料取值空间小，哈希可被穷举反推。

### 10.5 备份、导出与恢复边界

- **本地备份：** App 自己生成的本地备份在删除时一并清理该档案内容，或使备份整体失效。
- **恢复：** 恢复旧备份前，必须先读本机删除审计；备份中已被删除的档案默认不恢复，并提示用户。审计不存 ID，因此需要一个不可反推的匹配方法【待裁决：如何在不保留可反推信息的前提下识别“已删档案”】。
- **导出与外部副本：** 用户导出到设备外、云盘、系统备份（如 iCloud 整机备份）或他人处的副本，契约不承诺可删除；UI 删除确认页须写明这一点。
- 第一阶段没有云端同步与上传（【裁决 5】），因此没有服务器侧副本需要删除。

### 13.3 时辰精度与歧义输出（【用户裁决 G-2】，修正 1、2）

- CalculationInput 增 time\_precision：MINUTE / SHICHEN / UNKNOWN，必填。
- MINUTE：正常排四柱。
- **子时分界（本版锁定，非无争议，用户 2026-11-19 定稿）：** 子时 = 23:00–01:00，以 00:00 为界：晚子时 23:00–23:59，早子时 00:00–00:59。子时分界存在 23:00 换日与 00:00 换日两派；本版明确锁定 00:00 换日，这是本版决策，不是“无流派争议”。第一版锁死该基准，禁止隐式切换；后续流派差异通过显式配置项扩展，不得在第一版内切换。该锁定对应 CFG-01 = ye\_zi\_b（P-8.1），CFG-01 仍计入 8 项无默认值，第一版以版本锁定代替首次强制选择，B2 改为锁定值正向用例加其余三值拦截用例（【用户裁决 N-6】）。
- **子时时干统一按“00:00 之后那一日的日干”起：** 晚子时（23:00–23:59）时柱天干，以 00:00 之后那一日（即出生日日期的下一日）的日干起算；早子时（00:00–00:59）时柱天干，以 00:00 之后那一日（即出生日当天）的日干起算；整个子时（23:00–01:00）时柱唯一确定，日柱在 00:00 切换。
- **理由（用户原文）：** 时柱必须按六十甲子连续排。甲日亥时为乙亥，下一时辰必须是丙子；丙子只能由乙/庚日干起。晚子时若用当天日干起，会排出甲子，导致乙亥→甲子序列断裂，且同一天出现两个子时柱。为保时柱连续，晚子时必须用 00:00 之后那一日的日干起。
- **代价与声明：** 本方案存在“日柱用当天、时干用 00:00 之后那一日日干”的基准混搭。这是早晚子时派为保时柱连续而做的刻意选择，不是疏漏。契约在此显式声明，禁止实现者按“日干基准一致”自行修正。
- SHICHEN：时柱可排；若交节落在该时辰（2 小时窗口）内部，视为输入精度不足以排除跨交节，触发双解（§13.4）。子时（23:00–01:00）划分时，时柱按子时排，日柱严格按 00:00 换日切分（23:00–23:59 属出生日当天晚子时，00:00–00:59 属 00:00 后新一日早子时），日柱与时柱归属不得混同。晚子时与早子时的时柱天干，均以 00:00 之后那一日的日干起算，以保证时柱六十甲子连续；日柱在 00:00 切换，时柱在 23:00–01:00 内保持不变。本版显式接受“日柱当天、时干用 00:00 之后那一日日干”的基准混搭，禁止实现者按“日干基准一致”自行修正。
- SHICHEN 精度下若时辰为子时（23:00–01:00）：因跨越 00:00 换日点，日柱无法唯一确定，必须触发日柱双解：day\_pillar: { candidates: \[前一日, 当日\], ambiguous: true }。时柱天干统一按 00:00 之后那一日的日干起算，整个子时时柱唯一确定，hour\_pillar 输出单值且 ambiguous: false，不参与双解。requires\_user\_confirmation = true。子时换日双解与交节双解是两类独立触发条件，可同时生效、按柱叠加：换日双解只作用于日柱，交节双解只作用于年柱与月柱（立春时年柱、月柱均歧义）。两者不互相抑制，也不互相套用对方的候选规则。SHICHEN 精度输入 date D 且 shichen = 子时时，时间窗口定义为 \[D−1 日 23:00:00, D 日 01:00:00)，左闭右开（【用户裁决 G-2】结论 3，原 N-5 已裁决；写法按【用户裁决 B4-14】统一，原文“D 前一晚 23:00 至 D 当天 00:59”）。该窗口跨越 00:00 换日点，日柱候选为 \[D-1, D\]，day\_pillar.ambiguous = true；时柱按 D 的日干起算，唯一确定，hour\_pillar.ambiguous = false。SHICHEN 精度下其他时辰不跨日，日柱唯一，不触发双解。
- UNKNOWN：不 BLOCKED，进入三柱模式。年柱、月柱、日柱照常输出；时柱及强依赖时柱的派生项为 null，reason = HOUR\_UNKNOWN，degradation\_reasons 追加 HOUR\_UNKNOWN；chart\_type = THREE\_PILLARS。禁止任何默认时间回填，不得以 00:00、12:00 等代填。
- 生于交节当日且 UNKNOWN：同样视为不能排除跨交节，warning = CROSS\_TERM\_DAY\_HOUR\_UNKNOWN，给交节前后候选。三柱模式下交节候选只影响年柱、月柱，日柱始终单值；候选结构不得包含时柱字段。时辰 UNKNOWN 时日柱一律按登记的钟表日期 D 单值输出，不做真太阳时切日，也不因经度偏移给日柱双解；结果元数据与 UI 须声明：“因出生时辰未知，日柱按登记日期确定，未做真太阳时切日；若出生时刻经真太阳时换算后跨过 00:00，日柱可能变动。”（【用户裁决 N-3】2026-11-20）

**双解输出结构（按柱区分歧义）：**

- 无歧义的柱输出单值与 ambiguous: false。
- 有歧义的柱输出 candidates: \[A, B\] 与 ambiguous: true。非立春交节仅月柱有歧义，年柱保持 ambiguous: false；立春交节时年柱、月柱均 ambiguous: true；子时换日歧义时仅日柱 ambiguous: true，时柱保持 ambiguous: false。
- primary\_candidate：按固定规则（默认取交节前一侧候选项 A / 换日前一侧候选项 A，禁止随机）生成的默认建议值，仅用于 UI 默认高亮。用户未确认前（requires\_user\_confirmation = true），下游消费方必须按 ambiguous: true 处理，不得直接采用 primary\_candidate。primary\_candidate 只包含 ambiguous: true 的柱的默认建议值；无歧义柱不列入。
- 多类歧义并存时，candidates 按柱独立给出，互不覆盖；primary\_candidate 对每类歧义分别按固定规则生成。

```
year_pillar:  { value: A, ambiguous: false }   // 若立春跨年则改为 { candidates: [A, B], ambiguous: true }
month_pillar: { candidates: [A, B], ambiguous: true }
day_pillar:   { value: A, ambiguous: false }   // 若 SHICHEN 子时跨日则改为 { candidates: [前一日, 当日], ambiguous: true }
hour_pillar:  { value: A, ambiguous: false }   // SHICHEN 子时跨日时仍为单值（按 00:00 之后那一日的日干起），不双解
primary_candidate: { month_pillar: A }
requires_user_confirmation: true
```

### 13.4 交节边界（【用户裁决 G-3】，修正 1、6）

- **基准：** 所有节气交节时刻统一按北京时间 UTC+8 判定。交节是全球同一时刻，不随经度偏移。真太阳时只用于日柱、时柱切分，不得用于交节比较。用户输入非 UTC+8 时，先归一到 UTC+8 再判交节（归一沿用 §6.1 tz\_resolution 与 §11.1）。
- **告警层：** 距当月“节”的时刻 ±2 小时内，返回 boundary\_warning；立春放宽到 ±24 小时。
- **判定层：** 距交节 ±1 分钟内，或输入精度不足以排除跨交节（含 SHICHEN 覆盖交节时刻、UNKNOWN 落在交节当日），结果标 SOLAR\_TERM\_BOUNDARY\_AMBIGUOUS，输出交节前后候选，不得静默取整。
- 立春双解时，年柱、月柱一起给候选。
- **节气数据：** 由 Skyfield 生成 UTC+8 节气表，登记进 calendar\_data 并入 result\_fingerprint（§6.4、§6.5）；App 端只读预生成表。所用 JPL 星历文件定为 de440s.bsp（覆盖 1849–2150）【用户裁决 B4-1，2026-11-20】。
- **B4 回归：** 新增 solar\_terms\_1900\_2100 校验表；节气时刻与天文星历的误差容忍度 ≤ 1 分钟；用例覆盖交节前后 1 分钟、5 分钟、1 小时及 23:59→00:00 日柱切换，断言年柱、月柱、日柱的切换行为。23:59→00:00 与子时时柱连续性的用例见 §13.11 group 2，SHICHEN 子时与交节叠加见 group 3。

### E-MAP.3 使用规则

1. **迁移处理（按【用户裁决 A-7】与 S-5 改写，取代 Muse 使用规则 1）：** 39 条中标“已证实”的条目，迁移时只把“已证实”带入 claim\_status，不映射为 CROSS\_CHECKED 或任何 evidence\_status；evidence\_tier 与 evidence\_status 按实际资料逐条判定；来源不明者为 UNVERIFIED 并登记 missing\_evidence，不自动升级（§4.6）。
2. **一手版本定义：** 影印本/刻本/抄本原图已核对页、或国家标准/权威天文机构原文；排除一切未经影印页对校的转录本，含已知来源的电子转录本。
3. **交叉核对定义：** 至少两独立来源，其中至少一处为 E1 或 E2；摘要之间互见不等于对原文交叉核对。
4. **字段统一与聚合：** evidence\_status 与 verification\_status 统一为 §2.4 的六档枚举。聚合按维度分别进行，规则见 §4.3（【用户裁决 A-7；架构验收 3.10】）：evidence\_tier 取有效正式证据的最低等级，REJECTED 不参与；evidence\_status 保守聚合，任一为 UNVERIFIED/DISPUTED 时不得高于 CROSS\_CHECKED，全部为 REJECTED 时不产生有效支持状态；claim\_status 不按线性等级聚合，混合时显示 MIXED 并保留子项明细。聚合值只作展示与核查输入，不自动升级。
5. **用语统一：** “已核实/未核实”全文改写为枚举名，或在 §4.1 注明“已核实特指 PRIMARY\_VERIFIED”。
6. **“已证伪”不得映射为 REJECTED：** REJECTED 只用于伪引/误引的引用记录本身；主张级证伪用 claim\_status = 已证伪。
7. **“推断”档位：** 三源摘要一致或单源 → 至多 SINGLE\_SOURCE + 摘要互见（【用户裁决 K-1】，按本节第 3 条：摘要互见不算交叉核对），不得升为 CROSS\_CHECKED 或 PRIMARY\_VERIFIED，准入另查 claim\_status；E4 链条多源同样至多 SINGLE\_SOURCE；OP-16 / P-B-10 模拟按 E4 行。

### ENG.1 工程层限制（需在 v1.0 写明）

- **防篡改边界：** 触发器拒绝修改与删除、读取时校验哈希、治理记录串哈希链，只能防程序错误并发现篡改；本地数据库文件在用户手机上，不能阻止直接改文件。用户删除（§10）是唯一允许的删除路径。
- **P-B-10 若解封：** 引擎必须使用指定算法的伪随机数生成器，算法与种子同入指纹。
- **六爻摇卦：** App 内摇出的结果作为 CalculationInput 保存，不靠随机种子复算。
- **第一轮仍未解决项在本稿的位置：** F2 参数与变体统一（§3.4、§5）；F13 哈希与序列化（§1.2）；F14 原文不做 Unicode 规范化（§2）；F15 年代与日期类型（§3.3）；F16 流派与体系参照表（§3.5）；F20 删除与永久保留（§10）；F21 编号方案（§1.2）。
